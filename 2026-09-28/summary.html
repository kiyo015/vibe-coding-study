学習記録 ／ Day18 ／ 基幹システム開発

プラグインの配布とユーザー全体設定 — 安全柵を製品リポジトリに届ける

Day17で作ったDB破壊ガードは Study で作業している時しか効かなかった。dev-guard を絶対パスなしで sales-core に配布し、そこで実際にフックが発火することを対照実験つきで確かめた。個人の好みとチームの決まりも別のファイルに分けた。

2026-09-28対象: dev-guard 1.2.0 ／ sales-core ／ ~/.claude/CLAUDE.md段階1 / Day18

エグゼクティブサマリー

  1. dev-guard を GitHub からタグ固定で配布した。既存の公開リポジトリをそのままマーケットプレイスにしたので、新しく作るものはゼロ。sales-core の設定に絶対パスは無い。
  2. sales-core でフックが発火することを対照実験で示した。E2Eに1セル足し、6セルすべて合格（$0.4515）。
  3. マーケットプレイスの登録は名前ごとに1つで、開くたびに行き来する。それでも読み込まれる版は両プロジェクトとも意図どおりだった。仮説の半分が外れた。
  4. 個人とチームを「揃っている必要があるか」で分けた。会話の言語は個人、文書の言語はチーム。新しいセッションが両方を出典つきで読めていることを確認した。

タグで固定した理由。Study のリポジトリは学習記録も含めて毎日更新される。最新版を指すと、プラグインの変更がレビューなしで製品リポジトリに流れ込む。安全柵こそ「いつの間にか変わった」を避けたい。

03実測で見つけたこと — 登録は行き来する

マーケットプレイスの登録はマシン全体で名前ごとに1つ。開いたプロジェクトが毎回上書きするが、読み込まれる版はどちらも意図どおりだった。

sales-core を開いた直後、known_marketplaces.json の vibe-study が directory から github に上書きされていた。「最後に開いたプロジェクト次第で読み込まれる版が変わるのではないか」と仮説を立て、交互に開いて確かめた。

図表5: プロジェクトを交互に開いた結果
順番開いたプロジェクト登録ファイル読み込まれた dev-guard
1sales-coregithub（タグ固定）キャッシュの 1.2.0
2Studydirectory に戻ったStudy の作業中のコード
3sales-coregithub に戻ったキャッシュの 1.2.0

仮説の前半（登録は行き来する）は当たり、後半（読み込む版が狂う）は外れた。Study は開発用に作業中のコードを、sales-core は安定したタグ固定版を読む。影響を受けるのは両方を持つプラグイン作者のマシンだけなので、直さずに限界として記録した。E2E の実行中にもこの行き来が何度も起きていて、その中で全セルが通ったことが裏付けになった。

05つまずきと気づき

書き換えの結果は、目で見るまで信用しない。公開リポジトリの前提は、実測で安全を確かめた上で決める。

見出しを二重にした

guard-matrix.md の更新で、Edit の置換範囲に見出しを含めていないのに置換後の文字列に見出しを書き、「次に自動化するセル」が2回入った。grep で出現位置を数えて気付き、「想定した並びかどうか」を確認してから消すスクリプトで直した。

sales-core は意図的に公開している

PUBLIC であることを報告したところ、学習のエビデンスを公開するため意図的に公開しているとの回答だった。計画シートと daily-closeout スキルの「private」を直し（3か所）、「非公開化を提案しない。その代わり秘密情報は絶対にコミットしない」を記憶に保存した。

ローカルDBの接続文字列は公開しても入られないか

図表8: PostgreSQL への外部からの接続経路（実測）
確認したこと結果
待ち受けアドレス（netstat）0.0.0.0:5432：全インターフェースで待ち受けている
pg_hba.conf127.0.0.1/32 と ::1/128 だけ許可：他のPCからは認証の前に拒否
ファイアウォール5432番の受信許可ルールなし、ネットワークは「パブリック」：外からの接続は届かない

外からの接続は2段階で止まる。条件は、パスワードを他で使い回していないことと、postgres（スーパーユーザー）で接続しないこと。それでも接続文字列は user-secrets に置く。パスワードやポートは開発者ごとに違い、1つをコミットしても他のメンバーの環境では動かないため。
