## コマンド

- ビルド: `dotnet build`
- 全テスト: `dotnet test`
- 単一プロジェクトのテスト: `dotnet test tests/<対象>.Tests --no-restore`
- ツールの復元（clone直後に1回）: `dotnet tool restore`
- **表・列を変える時は `migration` スキルの手順に従う。** 生成 → SQL を `docs/migrations/` に出してレビュー → テスト用DBで確認 → 開発用DBにだけ適用

## ルールの書き方の約束

各ルールには **強制** か **お願い** を付ける。

- **強制** — ビルド・テスト・実行時・DB・設定・フックで技術的に止めている。漏れがあるものは、漏れ方まで書く
- **お願い** — ここに書いているだけ。AIも人も破れる。レビューで拾う

機械で判定できるルールは、できるだけ強制側に移す。CLAUDE.mdに「禁止」と書いただけで守られると思わないこと。**強制にしたら、対照実験（止める仕組みを外すと、本当に通ってしまうこと）で確かめ、確かめた日を書く。**

## 禁止事項

### 業務のデータとお金

| ルール | 種別 | どこで止めるか（sales-core の例） |
|---|---|---|
| 金額に `double`・`float` を使う | 強制（ビルド）＋お願い | `Directory.Build.props` で、ソースに語があればビルドエラー。型名を書かない double（`var x = 1.5`）は止まらないのでレビュー |
| 端数処理を金額型（`Money`）の外で行う | 強制（ビルド）＋お願い | BannedApiAnalyzers で `Math.Round` などを禁止し、例外は金額型のファイルだけ。**アナライザの版は SDK のコンパイラに合わせて固定する**（新しすぎる版は警告1つで黙って無効になった） |
| 消費税を明細ごとに丸めて合計する | 強制（テスト） | 税率ごとに1回だけ丸めるテスト。明細ごとに丸める実装を入れて落ちることを確かめる |
| 未出荷のまま請求する | 強制（型＋テスト） | 請求書の入口は売上だけを受け取り、売上は出荷確定からしか生まれない |
| 状態を飛び越える・逆戻りさせる | 強制（テスト） | 状態×操作の全組み合わせのテスト |
| 業務データを物理削除する | 強制（テスト・実行時・DB）＋お願い | アーキテクチャテスト（DLL に削除の API と SQL が無い）、保存時に削除の印を拒む、外部キーはすべて RESTRICT |
| 同時に変えて、後の保存が先の変更を上書きする | 強制（実行時） | 全表に版数の列（楽観ロック） |
| 締め済みの売上を二重に請求する | 強制（Domain・DB・版数） | Domain の検査は、関連を読み込んでいなくても外部キーで判定する（読み込みに頼ると素通りした） |

### 画面と権限

| ルール | 種別 | どこで止めるか（sales-core の例） |
|---|---|---|
| 画面から業務の判断（Domain の操作）や DB を直接使う | 強制（テスト） | アーキテクチャテストが画面の DLL を読む（`.razor` から生成されたコードも含む）。画面が呼んでよいのはユースケースだけ。**入れ子の型は名前の形が違い、検査を素通りした**（AIレビューが発見）ので、対照実験に入れる |
| 役割の表に無いことをする | 強制（テスト） | 権限の検査はユースケースの入口の1か所。**結合テストが業務ルール集の役割の表をそのまま読み**、役割×ユースケースの全組み合わせを確かめる。表の行とユースケースの対応の漏れ、公開メソッドの足し忘れも止める。表に無い操作は管理者だけ（書き忘れた時に拒む側へ倒す） |
| 画面でボタンを隠すことを守りにする | お願い＋強制（テスト） | 隠すのは使い勝手のため。守りは入口の検査。**隠し忘れと入口の検査の両方を外すと、権限の無い役割が登録できた**（2026-11-09、本物のブラウザで実測）。片方だけ外しても止まることと、両方外すと通ることの両方を対照実験にする |
| 役割を外した・無効にした利用者が、画面を使い続ける | 強制（テスト） | Cookie（開くたびの要求）と、開いたままの画面（Blazor Server の回線）の**両方**を、設定の間隔で DB と突き合わせ直す。**Identity は役割を変えても変更の印（セキュリティスタンプ）を変えない**ので、回線では役割そのものを比べる。測る前は最長14日（Cookie の期限）効かなかった（2026-11-10） |
| 時間の約束を、仕組みごとの間隔で決める | お願い | 仕組みが重なると間隔は足し算になる（Cookie 1分＋回線 1分で最悪約2分）。両方を約束の半分にする。確かめ直しの間隔を短くした副作用で、関係のないテストが経過時間しだいで落ちた（2026-11-11） |
| 画面で、前の操作で読んだデータを次の操作に持ち越す | 強制（テスト） | Interactive Server の回線は長く生きる。ユースケースは操作ごとに DB の文脈を作り、直接受け取るとアーキテクチャテストが落ちる |
| 入力の途中の値を、接続が繋がる前の描き直しで失う | 強制（テスト） | 入力のある画面はプリレンダーしない（先に静的に描かない）。テストが全画面の描画方式を確かめる。**本物のブラウザのテストで初めて見つかった**（bUnit では見えない） |
| 偽のリクエスト（CSRF）・ログインの Cookie | 強制（テスト） | ログイン・ログアウトの送信は印の検査を通す。ログインの Cookie は常に Secure（TLS を終える中継の後ろでも付ける）。テストは「Cookie を消させる応答が無いこと」を見る（Set-Cookie の有無で見ると、作り直しの Cookie で落ちる） |

**画面のテストの書き方（段階2で繰り返した失敗から）**
- 画面は読み込んでから中身を出し、テストはその中身を待つ。「出ない」ことを確かめる前に、読み込みが終わったことを先に確かめる
- テストの時計は、書いた日・実行する日と重ならない日付にする。タイムゾーンは業務の時刻（日本時間）で決める
- 本物のブラウザの端から端までのテストを、PR ごとの CI で流す。期待は役割の表から写す

### 開発の操作

| ルール | 種別 | どこで止めるか |
|---|---|---|
| 接続文字列・秘密情報をファイルに書く／読ませる | 強制（読み取り禁止）＋お願い | `permissions.deny` の `Read(./**/.env)` など。値は `dotnet user-secrets`。`dotnet user-secrets list` は実行しない（会話の記録に残る） |
| DBを壊すコマンド（`dotnet ef database drop`・`migrations remove`・SQLの`DROP`/`TRUNCATE`） | 強制 | `dev-guard` のフック（PreToolUse、Bash と PowerShell の両方） |
| force push・`git reset --hard` | 強制（漏れあり） | 2段。`permissions.deny` を **`Bash(...)` と `PowerShell(...)` の両方**に書く（Bash 用は PowerShell に効かない）。deny は先頭一致なので並べ替えると抜け、それを `dev-guard` のフックが止める |
| 再帰かつ強制の削除 | 強制（漏れあり） | `dev-guard` のフックだけ |
| テストが落ちたまま次に進む | 強制 | `dev-guard` が編集のたびに対応する `.Tests` を実行する。**テストプロジェクトの名前は `<対象>.Tests` に揃える**（この命名で走らせるテストを決めている） |
| ビルドかテストが落ちた変更を main に入れる | 強制（GitHub） | ルールセットで PR と CI 必須。管理者も例外なし |
| レビュー役がコードを書き換える | 強制 | `team-reviewer` サブエージェントに Read・Grep・Glob しか与えない |

### 安全柵の漏れ（実測）

- deny ルールは**先頭一致**。別名（`echo` と `Write-Output`）と `;`・`|` の複合は見るが、引数の並べ方や `git -C .` は見ない
- フックは「禁止する書き方の列挙」。変数・git のエイリアス・スクリプトファイルの中身は見えない。heredoc の本文に危険なコマンドの文字列があると、止めすぎる（誤検知）
- フックの PreToolUse の出力は `hookSpecificOutput.permissionDecision: "deny"` で返す（上の階層の `decision: "block"` は非推奨）
- **確実に禁じたい作業は、Bash・PowerShell を持たないサブエージェントに任せる**

## 開発の進め方

0. main に直接 push しない。ブランチ → PR → CI → スカッシュマージ
1. 仕様を決める（何を作るか、**何を作らないか**）
2. テストを先に書き、**狙った理由で落ちること**を確かめてから実装する
3. 仕込んだ誤り（対照実験）がテストで捕まることを確かめる
4. マージ前に `team-reviewer` でレビューする。渡すのは `git diff` と「何を実現する変更か」だけ（会話の経緯は渡さない）。指摘は実測してから直す・反論する
5. PR ごとの AI レビュー（CI）は必須のチェックにしない。判定は回ごとに揺れるので、マージの可否は人が決める
6. 対照実験を書く前に、「どのテストも通らない経路」を1行ずつ書き出し、その外側の誤りを1つは入れる（自分の対照実験は、自分が思いついた誤りしか入れない）
7. 段階の完了条件 → 確かめるテスト → 対照実験の結果の対応表を、段階の最初に設計の文書へ置き、毎日埋める。段階の終わりに、新しいセッション（文脈を切った状態）で、文書とテストだけから完了条件を確かめさせる（記録が散らばっていると「判断できない」になる。2026-11-11）
8. 件数・回数は、テストやコマンドの出力からそのまま写す

## 設定ファイルの置き場所

| 置き場所 | git | 用途 |
|---|---|---|
| `.claude/settings.json` | 共有 | チーム標準の権限・プラグイン・マーケットプレイス |
| `.claude/settings.local.json` | 共有しない | 個人の上書き。**`.gitignore` への記載が必須** |
| `~/.claude/settings.json` | — | 個人の全プロジェクト共通設定 |

- 優先順位は **ユーザー < プロジェクト < ローカル**。チームの `settings.json` は既定値で、強制ではない。全員に強制するなら組織の管理設定（managed settings）で配る
- **信頼を承認していないフォルダでは、プロジェクト設定の `permissions.allow` もプラグインも黙って無視される**
- **プラグインはタグ固定で配る**（`extraKnownMarketplaces` の `ref`）。更新はタグを上げる PR で行い、レビューを通す
- **マーケットプレイスは、マシン全体で名前ごとに1つ。** プラグインの作者が自分の機械でローカルのフォルダを登録する時は、配布用と別の名前にする。同じ名前だと、開いたリポジトリごとに登録が上書きされ、もう片方でプラグインが黙って読み込まれなくなる（2026-10-21 実測）

## 新しく参加した人へ

- 初日に `docs/onboarding.md` の手順で、**自分の機械で安全柵が実際に止めること**を確かめる。設定ファイルがあるだけでは効いているとは限らない
- 初回起動時に、プラグインと `.mcp.json` の MCP サーバーについて確認を求められる。承認する前に中身を読む（自分の PC でコードとして実行される）
- Windows では、同じフォルダが `C:/...` と `C:\...` の2通りで記録され、片方だけ信頼済みのことがある
- Windows の Smart App Control が、ビルドした署名なしの DLL を止めることがある（`0x800711C7`）。コードの誤りではないので、テストの成否を判断に使わない
