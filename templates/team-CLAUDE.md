## ルールの書き方の約束

このファイルの各ルールには、**強制** か **お願い** のどちらかを付ける。

- **強制** — 設定・hooks・サブエージェントのtoolsで技術的に止めている。AIも人も破れない（ただし漏れがあるものは明記する）
- **お願い** — このファイルに書いているだけ。AIも人も破れる。レビューで拾う

機械で判定できるルールは、できるだけ強制側に移す。お願いのまま置くのは、設計の妥当性や命名のように機械で判定できないものに限る。CLAUDE.mdに「禁止」と書いただけで守られると思わないこと。

## 禁止事項

| ルール | 種別 | どこで止めているか |
|---|---|---|
| force push・`git reset --hard`・`rm -rf` | 強制（漏れあり。下の表を参照） | `.claude/settings.json` の `permissions.deny` と `dev-guard` プラグインのフック。2つは漏れ方が違うので併用している |
| テストが落ちたまま次に進む | 強制 | `dev-guard` の PostToolUse フックが編集のたびにテストを実行し、失敗したら差し戻す |
| レビュー役がコードを書き換える | 強制 | `team-reviewer` サブエージェントに Read/Grep/Glob しか与えていない |
| 絶対パス・特定ユーザー名をコードや設定に書く | お願い | `team-reviewer` のレビュー観点で拾う。ツールが自動生成した設定にも混入するので、コミット前に差分を見る |
| 秘密情報（APIキー・トークン）をコミットする | お願い | `.env` は `.gitignore` 済み。それ以外のファイルへの直書きは機械では止めていない |
| マジックナンバー | お願い | レビューで拾う |

### 2つの層がそれぞれ何を止めるか（実測）

| 書き方 | deny ルール | フック 1.0.1 | フック 1.0.3 以降 | 結果（現在） |
|---|---|---|---|---|
| `git reset --hard HEAD` | 止める | 止める | 止める | 止まる |
| `git -C . reset --hard HEAD` | 抜ける | 止める | 止める | 止まる |
| `git reset HEAD~1 --hard` | 抜ける | 止める | 止める | 止まる |
| `git push --force origin main` | 止める | 止める | 止める | 止まる |
| `git push origin main --force` | 抜ける | 止める | 止める | 止まる |
| `git push -f origin main` | 止める | 抜ける | 止める | 止まる |
| `git push origin main -f` ／ `git push -uf` | 抜ける | 抜ける | 止める | 止まる |
| `git push origin +main` | 抜ける | 抜ける | 止める | 止まる |
| `git push \`（改行）`--force origin main` | 抜ける | 抜ける | 止める | 止まる |
| `rm -rf node_modules` | ルールなし | 止める | 止める | 止まる |
| `rm -fr` ／ `rm -r -f` ／ `rm -Rf` ／ `(rm -rf build)` | ルールなし | 抜ける | 止める | 止まる |
| PowerShellツールの `Remove-Item -Recurse -Force` ／ `ri -r -fo` ／ `del -Recurse -Force` | ルールなし | 対象外 | 止める | 止まる |
| PowerShellツールの `git push -f` など | 対象外 | 対象外 | 止める | 止まる |
| `cmd /c rd /s /q node_modules` | ルールなし | 抜ける | 止める | 止まる |
| 変数・gitのエイリアス・スクリプトファイル経由 | 抜ける | 抜ける | 抜ける | **止まらない** |
| （誤検知）`git commit -m "rm -rf を検知"` ／ `grep -rn "rm -rf"` ／ `git rm -r -f --cached` | — | 止めてしまう | 通す | 通る |
| （誤検知）ヒアドキュメントの本文で、行頭に `rm -rf` などを書く | — | 止めてしまう | 止めてしまう | **止まる（誤検知）** |

フックの列は、フックを別プロセスで起動して判定だけを見た実測で、`plugins/dev-guard/hooks/pre-bash-guard.test.js` に全ケースが入っている。deny の列は、無害なコマンド（`git branch --list`）に一時的な deny を付けて確かめた規則を当てはめた結果。

- **deny ルール**は `&&` で連結されたコマンドを分解してから照合するが、分解後は**先頭から一致するか**しか見ない。フラグの順序を変える、`git -C .` のようにオプションを前に挟む、のどちらでも抜ける。また `Bash(...)` ルールは**Bashツールにしか効かない**。PowerShellツールで同じコマンドを打つと素通りする
- **フック（1.0.1まで）**は1本の正規表現で、書いていない表記（`-f`、`-fr`、`+main`）は抜けた。matcherも `Bash` だけで、PowerShellツールは対象外だった（実測: PowerShellツールで `git reset --hard` を含む文字列を出力したら、何も言われずに実行された）
- **フック（1.0.3以降）**はコマンドを `&&`・`;`・`|` などで区切り、**コマンド名の位置にある単語だけ**を見て、その後ろのフラグを調べる。フラグの順序・まとめ書き・行の継続・PowerShellとcmdの書き方を拾う。引用符の中の文字列（コミットメッセージや検索語）や `git rm` は対象にしないので、ガードの話題そのものをコミットしても止まらない。1.0.2は `team-reviewer` のレビューで誤検知と抜けが見つかったため、1.0.3で直した
- それでも「禁止する書き方を列挙する」方式なので、変数展開（`$CMD`）、`git config alias.p "push -f"` で作ったエイリアス、スクリプトファイルの中身は見えない。**これは「うっかり」を防ぐ安全網であって、確実に禁じる仕組みではない。** 確実に禁じたい作業は、Bash・PowerShellを持たないサブエージェントに任せる
- 新しいシェル系ツールが増えたら、フックの matcher に足すこと。足さない限り、そのツールには何のガードも効かない

## 設定ファイルの置き場所

| 置き場所 | git | 用途 |
|---|---|---|
| `.claude/settings.json` | 共有 | チーム標準の権限・プラグイン・マーケットプレイス |
| `.claude/settings.local.json` | 共有しない | 個人の上書き。**`.gitignore` への記載が必須**（個人のgit除外設定に頼ると、他の人のPCではコミットに混入する） |
| `~/.claude/settings.json` | — | 個人の全プロジェクト共通設定 |

優先順位は **ユーザー < プロジェクト < ローカル**。各自のローカル設定でチーム設定を上書きできる（例: チームで有効にしたプラグインを自分だけ無効にする）。つまりチームの `settings.json` は「既定値」であって、全員に強制するものではない。全員に強制する必要があるルールは、組織の管理設定（managed settings）で配る。

なお、プロジェクト設定には「cloneしたリポジトリに勝手に効かせない」ための制限がある。

- **信頼を承認していないフォルダでは、プロジェクト設定の `permissions.allow` が無視される。** 初回に表示される信頼の確認を承認するまで、チームの許可ルールは効かない（実測: 未信頼の状態で起動すると `Ignoring 4 permissions.allow entries from .claude/settings.json: this workspace has not been trusted.` と表示された）。cloneしたばかりのリポジトリが、自分自身に権限を与えられないようにするための仕様
- 一部の設定は、プロジェクト設定に書くとそもそも読まれない（例: `autoMemoryDirectory`）

## レビュー

- マージ前に `team-reviewer` サブエージェントでレビューする。差分は呼ぶ側が `git diff` で作り、「何を実現する変更か」と一緒に渡す
- 作業中の会話の経緯や、自分の見立ては渡さない（先入観のないレビューにするため）
- 重大度（Critical / Important / Minor）の基準は `.claude/agents/team-reviewer.md` にある
- 指摘が間違っていると思ったら、根拠（コード・テスト）を示して反論してよい

## 新しく参加した人へ

- 初回起動時、プラグインと `.mcp.json` のMCPサーバーについて確認を求められることがある。承認する前に中身（`plugins/`、`.claude/mcp/`）を読む。これらは自分のPCでコードとして実行される
- プラグイン・MCPサーバーの追加や変更は、次回のセッションから反映される。サブエージェントの追加は、同じセッション内でも数ターン遅れる（しばらく反映されないこともある）
- Windowsでは、同じフォルダが `C:/...` と `C:\...` の2通りの表記で別々に記録され、片方だけ信頼済みになっていることがある。アプリでは権限が効くのに、ターミナルから起動すると効かない、という時はこれを疑う
