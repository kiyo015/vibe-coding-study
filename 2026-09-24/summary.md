# Day16 学習記録（2026-09-24）— 要件の骨格

基幹システム開発計画の2日目。コードを書く前に、**業務上の決まりごとを文書として確定させた**日。AIが実装で迷わないための「唯一の定義元」を作り、ER図を書いた時に保留していた論点を全部決めた。

## 今日行った処理

### 1. 保留していた8点を決めた

Day15でER図を書いた時、「業務の判断が要るので決められない」として残した論点があった。今日はそれを全部つぶした。決定と、その理由は以下の通り。

| 論点 | 決定 | なぜそう決めたか |
|---|---|---|
| 消費税の端数処理 | **四捨五入**（税率ごとに1回だけ） | 適格請求書（インボイス制度）の要件。明細ごとに税額を出して合計すると1円単位でずれる |
| 売上の計上基準 | **出荷基準**（出荷を確定した日） | 検収の報告を得意先から受け取らない運用のため |
| 締め日 | **得意先ごとに選ぶ**（5・10・15・20・25日・月末） | 得意先の都合に合わせる必要がある |
| 締め後に誤りが見つかったら | **翌月に赤黒で調整**。確定した請求書は変えない | 発行済みの請求書を書き換えると、得意先の手元の書類と食い違う |
| 受注の承認 | **税抜100万円以上**は管理者の承認まで出荷不可 | 基準額は変わりうるので、コードに直接書かず設定として持つ |
| 仕入先の請求書 | **自社の仕入計上と照合してから支払う** | 一致しないものを支払わないため |
| 単価 | 小数2桁まで（`numeric(15,2)`） | 単位当たり価格に銭が出る商品がある |
| 数量 | 小数3桁まで（`numeric(15,3)`） | 重量・長さで売る商品がある |

単価と数量に小数を許したことで、**新しい論点が1つ派生した**。単価×数量に端数が出るため、明細金額をどう丸めるかを決めなければならない。これは消費税と揃えて「**明細ごとに1回、四捨五入して円単位**」とした。

元の8点だけを答えて終わりにせず、「その決定から何が導かれるか」を辿ったことで、実装時に迷う箇所を1つ先に潰せた。

### 2. 3つの文書を作り、1つを更新した

`sales-core/docs/domain/` に置いた。

| 文書 | 行数 | 役割 |
|---|---|---|
| `business-rules.md` | 102 | **業務上の決まりごとの唯一の定義元。** 金額・端数・状態・締め・承認・購買・在庫・データの扱い |
| `glossary.md` | 60 | 用語と、コード上の名前（英語）の対応 |
| `business-flow.md` | 78 | 販売・購買の流れ、受注の状態遷移、締めと請求（図4枚） |
| `er-diagram.md` | 558（46行更新） | 仕入先請求書と照合の表を追加し、決定を反映 |

**用語集を作った理由は「AIが言葉を取り違えないため」。** 同じものを別の名前で呼ぶと、実装がぶれる。特に紛らわしい組み合わせを表にした。

| 区別すべき言葉 | 違い |
|---|---|
| 受注 と 売上 | 受注は「注文を受けた」段階。売上は「出荷を確定した」段階。受注しただけでは売上にならない |
| 出荷先 と 請求先 | 商品を送る先と、請求書を送る先。同じとは限らない（支店に出荷し本社に請求する） |
| 入荷 と 検収 | 届いただけか、確認して合格としたか。仕入になるのは検収した数量 |
| 在庫 と 引当可能数 | 実際にある数と、そこから引当済みを引いた数 |
| 取消 と 削除 | 取消は状態を変えるか赤伝を立てること。**削除はしない** |

### 3. 決定の変更がER図に波及した

「仕入先の請求書と照合してから支払う」と決めたことで、ER図に足りない表があることが分かった。

- `supplier_invoices`（仕入先から受け取った請求書）を追加
- `supplier_invoice_matches`（自社の仕入計上との照合結果）を追加
- `payment_allocations`（支払の消し込み）の参照先を、発注から**仕入先請求書**に付け替えた

業務の決定を先にしたことで、テーブルの過不足が見つかった。**ER図だけ先に書いても、決めごとが無ければ正しいかどうか判断できない**という例。

### 4. CLAUDE.mdからの参照方法を選んだ

4つの文書のうち、**`business-rules.md`だけを`@`で常時読み込む**ようにした。

```markdown
@docs/domain/business-rules.md
```

残り3つはパスを表に書くだけにした。

| 文書 | いつ読むか |
|---|---|
| `docs/domain/glossary.md` | 業務の言葉を扱うとき |
| `docs/domain/business-flow.md` | 業務の順序や状態遷移を扱うとき |
| `docs/domain/er-diagram.md` | テーブルやエンティティを追加・変更するとき |

`@`で書いた参照は**全文が常に文脈に載る**（Day2で計測した通り）。558行のER図まで常時読ませると、毎回の会話が重くなる。一方で金額の端数処理を間違えると請求額の誤りに直結するので、業務ルール集だけは常に見えている状態にした。

### 5. 完了条件を実測で確認した

今日の完了条件は「新しいセッションで『請求書の端数処理はどうする？』と聞くと、業務ルール集の内容で答えが返る」。自分で「書いたから大丈夫」と判断せず、**別のセッション（ヘッドレス実行）で実際に質問した**。

```bash
cd sales-core && echo "..." | claude -p --model haiku --strict-mcp-config
```

返ってきた答え:

> 1. **消費税の端数処理**：税率ごとに1回、四捨五入。明細ごとには行わない（インボイス要件）
> 2. **売上計上**：出荷確定日に計上
> 3. **締め日**：得意先ごと選択（5日・10日・15日・20日・25日・月末）

3問とも業務ルール集どおり。**書いた文書が実際にAIの回答を変えていること**を確認できた。

図も描画して確認した。業務フロー4枚とER図7枚、合わせて**11枚すべて構文エラーなし**。Mermaid 11で`mermaid.parse()`を全ブロックに通し、`mermaid.run()`で実際に描画させた。

## つまずき

### ワークスペースの信頼が未承認で、許可ルールが無視されていた

**症状** — ヘッドレス実行の標準エラー出力に、見慣れない警告が出た。

```
Ignoring 6 permissions.allow entries from .claude/settings.json:
this workspace has not been trusted.
```

**原因** — Day15で`sales-core`に`.claude/settings.json`を作り、`dotnet build`・`dotnet test`・`git status`などを許可するルールを6件書いた。しかし**そのワークスペースで一度もClaude Codeを対話起動して信頼を承認していなかった**ため、許可ルールが丸ごと無視されていた。

「設定ファイルに書いた」と「設定が効いている」は別だという、Day11・Day14で繰り返し学んだことがまた出た。今回は**警告が標準エラー出力にしか出ない**ので、標準出力だけを見ていたら気付かなかった。

**対策** — 本人が`sales-core`でClaude Codeを起動し、信頼を承認した。承認後、3つの方法で解消を確認した。

| 確認方法 | 結果 |
|---|---|
| `~/.claude.json`の該当プロジェクト | `hasTrustDialogAccepted: true` |
| 再度ヘッドレス実行し、標準エラー出力を見る | 警告が出ない |
| `git status --short`を実行させ、`--output-format json`の`permission_denials`を見る | `[]`（拒否ゼロ＝許可ルールが効いている） |

3つ目が本命。**警告が消えたことは「無視されなくなった」証拠でしかなく、「許可が実際に働く」証拠ではない。** 実際に許可対象のコマンドを実行させて、拒否が起きないことまで見た。費用は$0.036。

信用情報の入力や信頼チェックの回避は代理で行わず、本人に承認してもらう方針を守った。

### シェルのエスケープでまた詰まった

Mermaidの検証ページを作る時に、Windowsのパスを含むスクリプトを`node -e`でシェル経由に渡そうとして、バックスラッシュが消えた。Day15でも同じことをやっている。

**対策** — パスは**スラッシュ区切り**で書き、少しでも長いスクリプトは`node -e`ではなく**ファイルに書いてから実行する**。これを今日の習慣にした。

## 今日学んだこと

### 設計の順番：決めごと → データ構造 → コード

今日いちばん効いたのは、**業務の決定をER図より先に確定させるべきだった**という逆順の発見だった。Day15でER図を先に書き、今日決めごとをしたら、表が2つ足りないことと参照先が違うことが分かった。

ただし完全な手戻りではなかった。**ER図を書いたからこそ「これは決めないと書けない」という論点が5つ洗い出せた**。決めごとだけを先に考えても、何を決めるべきかは出てこなかったと思う。

| 順番 | 得られるもの | 足りないもの |
|---|---|---|
| ER図だけ先 | 決めるべき論点が具体的に出る | 決めていないので正しいか判断できない |
| 決めごとだけ先 | 判断はできる | 何を決めるべきか網羅できない |
| **ER図 → 決めごと → ER図の修正** | 両方 | 1往復ぶんの手間 |

1往復する前提で進めるのが現実的だと分かった。

### 「唯一の定義元」を決めると、変更の手順も決まる

業務ルール集の冒頭に「**ここを変える時は、コード・テスト・この文書を必ず一緒に直す**」と書いた。この一行があると、後から税率や締め日が変わった時に何をすればいいかが定まる。Day24で`domain-rule-change`スキルとして手順化する予定。

定義元が複数あると、どれが正しいか分からなくなる。**実装より先に「どこを見れば正しいか」を1か所に決めておく**のが、AIと作る時にはより重要になる。人間なら「たぶんこっちが新しい」と察するが、AIは両方読んで矛盾したまま実装する。

### 完了条件は「別のセッションで測る」

今日の完了条件を、自分の判断ではなく**新しいセッションへの質問**で確かめた。同じセッション内で確認すると、会話の履歴に決定内容が残っているので、文書を読まなくても答えられてしまう。**文脈をリセットした状態で聞いて初めて、文書が効いているかが分かる。**

これはDay12以降のヘッドレス実行の使い方がそのまま活きた。学習用に覚えた仕組みが、実プロジェクトの検証手段になっている。

## 気づき・発見

**警告は標準エラー出力に出る。** 今回の信頼の警告は、標準出力（AIの回答）には一切出なかった。自動化した処理で標準出力だけを拾っていると、この種の警告は永久に見えない。Day19以降でCIを組む時、**標準エラー出力も記録に残す**ようにする。

**決定の理由を一緒に書くと、後で変えられる。** 「四捨五入」とだけ書くと、後から見た人が「なぜ切り捨てではないのか」を判断できない。「インボイス制度の要件」と理由を添えたので、制度が変われば直せる。逆に理由の書けない決定は、決め方を疑ったほうがいい。
