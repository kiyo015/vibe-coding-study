06つまずき — 設定が効いていなかった

sales-coreのワークスペースが未信頼のまま運用されており、書いてあった許可ルール6件が丸ごと無視されていた。

症状。ヘッドレス実行の標準エラー出力に警告が出ていた。

Ignoring 6 permissions.allow entries from .claude/settings.json: this workspace has not been trusted.

原因。Day15で .claude/settings.json に許可ルールを6件書いたが、そのワークスペースで一度も対話起動して信頼を承認していなかった。「設定ファイルに書いた」と「設定が効いている」が別だという、Day11・Day14で繰り返し学んだことが再発した。今回は警告が標準エラー出力にしか出ないため、標準出力だけを見ていたら気付かなかった。

対策。本人が信頼を承認したうえで、3つの方法で解消を確認した。

図表6: 解消の確認方法と結果
確認方法結果何の証拠か
~/.claude.jsonの該当プロジェクトhasTrustDialogAccepted: true承認が記録されている
再度ヘッドレス実行し標準エラー出力を見る警告が出ない無視されなくなった
git statusを実行させpermission_denialsを見る[]（拒否ゼロ）許可が実際に働いている

出所: claude -p --output-format json の実行結果（費用 $0.036）

3つ目が本命。警告が消えたことは「無視されなくなった」証拠でしかなく、「許可が実際に働く」証拠ではない。許可対象のコマンドを実行させ、拒否が起きないことまで見た。信頼の承認そのものは本人が行い、代理で回避はしていない。

もう1件 — シェルのエスケープ

Windowsのパスを含むスクリプトを node -e でシェル経由に渡し、バックスラッシュが消えた。Day15でも同じことをしている。対策として、パスはスラッシュ区切りで書き、少しでも長いスクリプトはファイルに書いてから実行することにした。

07今日学んだこと

定義元を1か所に決めておくことは、人間相手より AI と作る時のほうが効く。

「唯一の定義元」を決めると、変更の手順も決まる

業務ルール集の冒頭に「ここを変える時は、コード・テスト・この文書を必ず一緒に直す」と書いた。定義元が複数あると、どれが正しいか分からなくなる。人間なら「たぶんこちらが新しい」と察するが、AIは両方読んで矛盾したまま実装する。Day24で domain-rule-change スキルとして手順化する。

警告は標準エラー出力に出る

今回の信頼の警告は、標準出力（AIの回答）には一切出なかった。自動化した処理で標準出力だけを拾っていると、この種の警告は永久に見えない。Day28以降でCIを組む時は標準エラー出力も記録に残す。

決定の理由を一緒に書くと、後で変えられる

「四捨五入」とだけ書くと、後から見た人が「なぜ切り捨てではないのか」を判断できない。「インボイス制度の要件」と理由を添えたので、制度が変われば直せる。逆に理由の書けない決定は、決め方を疑ったほうがいい。
