## 今日学んだこと

### 1. ヘッドレス実行 `claude -p` が自動化の土台

対話画面を開かずに1往復だけ動かす形。`--output-format json`を付けると機械で読める。

| フィールド | 使い道 |
|---|---|
| `result` | 応答本文 |
| `is_error` / 終了コード | 分岐 |
| `total_cost_usd` | **1回いくらか**（定期実行の予算管理） |
| `permission_denials` | 無人実行が権限で詰まったことの検知 |
| `usage.cache_creation_input_tokens` / `cache_read_input_tokens` | コストの正体 |

### 2. コストの正体は「指示の長さ」ではなく「毎回積み直す文脈」

`2+3`を聞くだけで**$0.095**だった。入力トークンは**2**しかないのに、キャッシュ作成21,898・キャッシュ読み取り37,789ある。CLAUDE.md・スキルの説明文・サブエージェントの説明文・ツール定義・プラグイン・MCPという、Day10で測った「常時コスト」が、そのまま1回ごとの請求になっている。

対話セッションなら1回積めば使い回せるが、**定期実行は毎回新しいセッションなので毎回積み直す**。

| 条件 | 1回 | 平日毎日（月22回） | 年 |
|---|---|---|---|
| 既定（Sonnet 5） | $0.0749 | $1.65 | $19.55 |
| `--model haiku` | $0.0339 | $0.75 | $8.85 |
| `--strict-mcp-config`（`.mcp.json`を読まない） | $0.0742 | — | — |
| haiku＋`--strict-mcp-config` | $0.0260 | $0.57 | $6.79 |

`--strict-mcp-config`がほぼ効かなかったのは、今日はMCPサーバーを承認していないため元々読み込んでいなかったから。**効くはずの対策も、測らなければ「効いた気になる」だけ。**

### 3. 無人実行で最初に詰まるのは権限

最初に作った健康診断は、異常時に`claude -p`へ要約させる作りだった。返ってきたのは要約ではなくこれ。

> 実行に承認要る。`node checks/health-check.js` 実行許可くれ。

**要約を頼んだのに、自分でチェックを実行しようとして権限の確認で止まった。** 人がいれば押せるが、無人では誰も押さない。

対策は2通りあり、両方使った。

1. **道具を与えない** — `--tools ""`で全ツールを禁止する。要約だけなら読む手段も実行する手段も要らない（Day11の`team-reviewer`と同じ「お願いでなく`tools`で保証する」考え方）。付けた後は狙いどおり3行で返った（$0.027・6秒）
2. **先に許可しておく** — 実行させたい場合は`.claude/settings.json`の`permissions.allow`に入れる

### 4. 定期実行は「AIを呼ぶ回数」を設計する

健康診断スクリプトの芯は、**事実の収集（決定的な処理）と判断の説明（AI）を分けた**こと。

- テストの成否・依存・gitの状態は終了コードで確実に判定できる。ここにAIを挟むと遅く・高く・不安定になる
- **全部OKならAIを呼ばない**ので、正常な日のコストは**0**
- 異常時だけ、失敗した項目の出力（末尾2,000文字）だけを渡す。成功分は渡さない

月1回異常が出る前提なら月$0.03。毎回AIに報告させる設計（月$0.75〜1.65）より2桁安い。**効くのはモデル選択より呼ぶ回数の設計。**

### 5. 「異常」の定義は、放置したら損害が出るかどうかで決める

最初は「未コミットがあればNG」にしていたが、作業中は常にNGになる。**毎日鳴る警告は誰も見なくなる。**

```js
// 未コミットは作業中なら常にあるので異常にしない(毎回鳴る警告は誰も見なくなる)。
// 未pushのコミットは、このPCが壊れたら失われる分なので異常として扱う。
ok: unpushed === 0,
```

### 6. スケジュールの3層と、それぞれの性質

| | hooks（Day6） | `/loop` | 定期タスク（アプリ／OS） |
|---|---|---|---|
| きっかけ | ツール使用などのイベント | セッション自身 | 時刻 |
| 前回の記憶 | — | **ある**（同じセッションが続く） | **ない**（毎回まっさら） |
| 生存期間 | 設定にある限り | セッションを閉じたら消える | ディスクに残る |
| 人がいない時 | 動かない | 動かない | 動く |
| 向く用途 | 規約の強制・編集後のテスト | 作業中に待つ（CI完了待ち・ログ監視） | 毎日の点検・レポート |

**毎回まっさら**という性質が、定期タスクの指示文の書き方を決める。この会話の文脈は一切引き継がれないので、作業フォルダ・コマンド・出力形式・やってはいけないこと（コードを修正しない）・迷った時の振る舞い（推測と明記）まで全部書く。実際、発火したセッションの先頭にはこう入っていた。

> This is an automated run of a scheduled task. The user is not present to answer questions.

### 2種類のスケジューラに登録

| 登録先 | 設定 | 動く条件 | 実行の主体 | 結果 |
|---|---|---|---|---|
| アプリの定期タスク | `0 9 * * 1-5`（平日9時） | アプリ起動中（閉じていたら次回起動時） | Claudeのセッション（判断できる） | セッションとして残り通知が来る |
| Windowsのタスクスケジューラ | `schtasks /SC DAILY /ST 09:30` | **アプリを開いていなくても動く** | バッチがスクリプトを直接実行 | `checks/schtasks.log`に追記 |

アプリ側の指示文は`~/.claude/scheduled-tasks/vibe-study-health-check/SKILL.md`に保存される。**スキルと同じ形式**で、Day3で学んだ仕組みが定期タスクの実体になっている。

### 1回発火して確認した

- **Windows側:** `schtasks /Run` で`exit=0`。ログにも結果が残った
- **アプリ側（1回目）:** `Bash`を呼んだところで**権限の確認待ちのまま20分以上停止**。本人が承認して完走（「異常なし（全7件）」）
- **アプリ側（2回目）:** 承認が記憶され、**確認なしで完走**（3往復・約2分）

2回目の報告はこうだった。

> 異常 1件（全7件）
> - git の状態: 未push コミット1件 (未コミット0件)

直前に作ったDay12のコミットがpushされていないことを、**仕組みが自力で見つけた**。pushしてから再実行すると「異常なし」に戻った。**検知が本物であること（いつも同じ答えではないこと）と、直せば静かになることの両方を確認できた。**

### `/loop`を2周だけ回した

`/loop 90s ...`で指定したが、cronは90秒を表せないので**2分ごと**に丸められた（`*/2 * * * *`）。

- 1周目: 健康診断を実行 → `history.log`は6行、末尾`08:25:13.757Z`
- 2周目: 実行 → **7行**、末尾`08:26:27.621Z`。**ファイルを読み直さずに「前回は6行」と比較できた**
- 2周したので`CronDelete`で停止

ループの実体はメモリだけで、ディスクには何も書かれない。セッションを閉じれば消え、放置しても7日で自動終了する。**この会話の文脈ごと毎回課金される**ので、大きなセッションで長時間回すのは高い。

## つまずき（3つとも自動化特有）

| つまずき | 症状 | 原因と対策 |
|---|---|---|
| 無人実行が権限で止まる | 20分以上`running`のまま | 確認を押す人がいない。`--tools ""`で道具を与えない／許可ルールを先に入れる |
| バッチが文字化けして失敗 | `exit=9009` | `.cmd`をUTF-8で書き日本語コメントを入れると、cmd.exeがShift-JISとして読んで壊し、命令として解釈する。`chcp 65001`を先頭に足しても直らず、**コメントを英数字だけにして解決** |
| バッチが見つからない | `'health-check.cmd' は認識されていません` | 起動時のカレントディレクトリが想定と違う。`%~dp0`（自分のある場所）を基準にして、絶対パスもカレント依存も排除 |

3つに共通するのは、**対話では表に出ない前提（人がいる・文字コード・カレントディレクトリ）が、無人実行で初めて牙を剥く**こと。

## 気づき・発見

- Day10で測った「機構ごとの常時コスト」が、定期実行では**1回ごとの請求**として跳ね返る。コンテキスト設計はそのままコスト設計
- 定期実行で怖いのは「いつも緑」と「いつも赤」。どちらも人が見なくなる。**状態に応じて変わることを、異常を意図的に作って確認する**べき
- 生成物（ログ・報告書）はgit管理から外した。共有するのは**仕組み**であって実行結果ではない
- Day11で作った許可ルールの仕組みが、そのまま無人実行の詰まり解消に使えた。「チームで配れる形」＝「無人でも通る形」
