01ヘッドレス実行と費用構造

claude -pは対話画面を開かずに1往復だけ動かす形。出力をJSONで受け取ると、応答・終了コード・料金・権限拒否まで機械で読める。

表1　--output-format json で返る主なフィールド
フィールド使い道

is_error / 終了コードスクリプト側の分岐
total_cost_usd1回いくらか。定期実行の予算管理

usage.cache_creation_input_tokens ／ cache_read_input_tokensコストの正体（今回 21,898 ／ 37,789）

2+3を聞いただけで$0.0749。入力トークンは2しかない。金額を作っているのは、起動のたびに積まれるCLAUDE.md・スキルの説明文・ツール定義・プラグインで、対話なら1回積んで使い回せるものが、定期実行では毎回積み直される。

実測値。いずれも同じ質問（「2+3の答えだけを数字で返して」）を1回実行した結果。

02AIを呼ぶ回数を設計する

事実の収集は決定的な処理に任せ、AIは異常時だけ呼ぶ。正常な日のコストが0になり、毎回呼ぶ設計より2桁安くなる。

表2　運用コストの見通し（平日毎日・実測値からの試算）
設計1回月（22回）年（261回）
毎回AIに報告させる（既定モデル）$0.0749$1.65$19.55
毎回AIに報告させる（haiku）$0.0339$0.75$8.85
異常時だけAIを呼ぶ（今日の設計・月1回異常が出る前提）$0$0.03$0.41

「異常」の定義も設計対象。最初は未コミットがあればNGにしていたが、作業中は常にNGになる。毎日鳴る警告は誰も見なくなるので、未pushのコミット（PCが壊れたら失われる分）だけを異常に変えた。

「毎回まっさら」という性質が、指示文の書き方を決める。会話の文脈は一切引き継がれないので、作業フォルダ・コマンド・出力形式・やってはいけないこと・迷った時の振る舞いまで全部書く。発火したセッションの先頭には、実際にこう入っていた——This is an automated run of a scheduled task. The user is not present to answer questions.

041回発火して確かめた

仕組みが本当に働いているかは、異常を意図的に作って確かめる。「いつも緑」と「いつも赤」はどちらも見られなくなる。

表4　発火の結果
実行結果
Windowsのタスクスケジューラ（手動発火）exit=0。ログに結果が残った
アプリの定期タスク（1回目）権限の確認待ちで20分以上停止。本人が承認して完走（「異常なし（全7件）」）
アプリの定期タスク（2回目）承認が記憶され、確認なしで完走（3往復・約2分）

2回目の報告は「異常 1件（全7件）／ git の状態: 未push コミット1件」。直前に作ったコミットがpushされていないことを、仕組みが自力で見つけた。pushしてから再実行すると「異常なし」に戻り、検知が本物であること（いつも同じ答えではないこと）と、直せば静かになることの両方を確認できた。

/loopを2周だけ回した

  • 指定した90sはcronで表せないので2分ごとに丸められた（*/2 * * * *）
  • 1周目はログ6行、2周目は7行。ファイルを読み直さずに「前回は6行」と比較できた——同じセッションが続いている証拠
  • 実体はメモリだけでディスクには何も書かれない。セッションを閉じれば消え、放置しても7日で自動終了する
  • 会話の文脈ごと毎回課金されるので、大きなセッションで長時間回すのは高い
