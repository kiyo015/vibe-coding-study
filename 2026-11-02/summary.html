01受注の画面

ボタンを出す規則と、操作を許す規則を同じ所に置いた。画面に出るボタンと、押して通る操作が食い違わない。

画面内容
/orders一覧（全員）。新しい順、状態は日本語。登録への入口は営業と管理者にだけ出す
/orders/new登録。商品を選ぶと標準単価が入り、書き換えられる。無効のマスタは選択肢に出さない。受注日の初期値は日本時間の今日
/orders/{id}詳細と、承認・取消のボタン
  • URL を直接開いた時も拒む。登録の画面は最初に Permissions.Require を呼ぶ。
  • 開いている間に、ほかの人が状態を変えた時:押すと 409 の理由が出て、今の状態を読み直して出す。読み直しに失敗しても元の理由を出す。
  • SalesOrderUseCases.ListAsync を足し、メニューに「受注」を足した。

02税区分と税率をマイグレーションで入れた

本人の決定。物理削除を止めるテストが、巻き戻しの DELETE も止めた。行は巻き戻しても残す。

質問本人の決定
開発用 DB に税区分が無く、画面から商品も受注も登録できない（税区分の登録の操作は無い）。どうやって DB に入れる？マイグレーションで入れる。標準 STD 10%・軽減 RED 8%、どちらも 2019-10-01 から
  • マイグレーション SeedTaxCategories。作成者は migration（業務ルール集「8.」に書いた）。
  • 手順のスキルは「データを入れない」としている。法令で決まり、どの環境でも同じ値なので、税区分と税率だけを例外として書き足した。
  • 最初の Down の DELETE は NoPhysicalDeleteTests が止めた。Down は何もせず、Up はもう一度当てても重ならない（ON CONFLICT DO NOTHING）。
  • SQL を書き出して見て（DROP・型の変更・CASCADE なし）、テストの DB で確かめてから開発用 DB に当てた。

反映先: 決定の記録 2026-11-02・業務ルール集「2.」「8.」・ER 図・マイグレーションの手順のスキル。

07今日学んだこと

テストのデータ作りや手元の時計が、本番との違いを隠す。ブラウザと UTC の時計で初めて見えた。

  1. ブラウザで操作して、初めて分かることがある。税区分が無いと何も登録できない。テストはデータ作りで税区分を自分で作っていた。
  2. テストの時計が手元の機械に頼ると、日本時間の誤りを見逃す。手元は日本時間なので通っていた。UTC に固定して RED になった。
  3. 決まりをテストで守らせると、思わぬ所でも効く。物理削除を止めるテストが、マイグレーションの巻き戻しも止めた。
  4. ボタンを出す規則と操作を許す規則を同じ所に置く。画面のボタンと Domain の操作が同じ SalesOrderStatusRules を使う。
