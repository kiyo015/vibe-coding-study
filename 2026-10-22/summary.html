01画面の骨格

画面は Application だけを参照し、DB とユースケースの登録も API と共通の1か所（AddSalesCore）に置いた。

  • テンプレートの英語の文言を日本語にした。エラー画面には問い合わせ番号だけを出し、例外の中身は出さない
  • http://localhost:5159 で起動を確かめた。bUnit のテストは RED（Hello, world!）を見てから直した

02画面から Domain を直接使わない

権限の検査はユースケースの入口に置くので、画面が Domain を直接触ると素通りできる。Web の DLL（.razor から生成されたコードを含む）を読んで止める。

図表2: 対照実験（Home.razor に誤りを入れて WebLayerTests を流す）
入れた誤り結果
Money.Of(1m).Yen を呼ぶ失敗（Money.Of・get_Yen を検出）
@inject SalesCoreDbContext失敗（Infrastructure の型の参照）
e is BusinessRuleException（例外の型で判定するだけ）通る（許す）
Domain の入れ子の型のメソッド（2回目の AI レビューの指摘）直す前は素通り → 直した後は失敗（NestedProbe+Inner.Value）
画面に DELETE FROM の SQL失敗（Web を物理削除の検査の対象に足した後）

DLL を読む部品は AssemblyMetadata に切り出した（AI レビューの Minor）。切り出した後も、Money.Of の誤りと Application の DbContext.Remove を検出することを確かめた。

03画面を足して見つかった穴

金額の決まりも dev-guard も .cs を前提にしていた。新しい種類のファイルを足したら、既存の守りがそれを見ているかを、誤りを入れて確かめる。

図表3: .razor の誤りと、それぞれの守り

アナライザはコンパイル後のコードを見るので .razor も止まった。SALES001 はファイルの一覧（Compile）を見ていて、.razor は Content に入るので素通りした。守りの種類で、見ている範囲が違う。
