### 4. 持ち越しを片付けた

**.razor の SALES001 を、毎回テストで確かめる（`RazorMoneyRuleTests`）**
- 画面の部品（.razor）は Compile でなく Content に入る。`src/Directory.Build.props` は Content も足して double・float を調べている。SDK の更新で Content の扱いが変わると、気付かずに素通りに戻る。
- テストは、Web と同じ SDK の小さなプロジェクトを作り、検査の段階（`SalesCoreMoneyRules`）だけを `dotnet msbuild` で動かす。
- SDK と対象のフレームワークは、本物の `SalesCore.Web.csproj` から写す（AI レビュー2回目）。

| 対照実験 | 結果 |
|---|---|
| props から「.razor を調べる」行を外す（1回目） | 3件とも落ちた（decimal まで） |
| 小さなプロジェクトに `.cs` も置き、同じく外す（2回目） | **double・float の2件が落ち、decimal は通った** |
| 元に戻す | 3件とも合格 |

- 1回目は、小さなプロジェクトに `.cs` が無かった。Compile が空になり、検査が空のパスを読んで別の理由（MSB4184）で落ちていた。本物の Web と同じく `.cs` も置く形に直した。
- テストは終了コードと「SALES001」の出力の両方を見る。別の理由で落ちても、誤って通らない。

**ログアウトのテストは、厳格な解析に替えた**
- `SetCookieHeaderValue.ParseList` は、解析できない値を黙って捨てる。崩れた削除の Set-Cookie を見逃し、「消させる応答が無い」の確かめが誤って通る。
- `dotnet fsi` で、崩れた値を混ぜて確かめた。`ParseList` は2件中1件を黙って捨て、`ParseStrictList` は `FormatException` を投げた。
- `ParseStrictList` に替えた。

**`Routes.razor` の「権限がありません」のテストは書かなかった**
- この表示は、役割を指定した画面（`[Authorize(Roles=…)]`）に、その役割の無い人が来た時に出る。今は役割を指定した画面が無いので、辿り着けない。
- 役割を指定した画面を作る日まで持ち越す。

## 今日学んだこと

- **レビューに業務の判断を決めさせない。** 5回のうち4回は、業務の判断が要る指摘だった（残高の税、見積の状態、単価の改定、消込と繰越）。ここで推測して決めず、業務ルール集「9.」に「作る日の作業の前に本人に聞くこと」として書いた。設計の日は、決まっていないことを見つける日でもある。
- **本人の決定どうしが矛盾することがある。** 「古い請求書から充てる」と「繰越の形式」は、どちらも単独では自然な決定だった。組み合わせて初めて、二重に数えると分かった。数値の例を書くと、矛盾がはっきり見えた。
- **対照実験が全部落ちたら、落ちた理由を見る。** 1回目は decimal まで落ちた。「検査が効いた」ではなく、別の理由（空のパス）で落ちていた。止まらない側の対照（decimal）を入れておいたので気付けた。
- **小さな再現は、本物と同じ形にする。** `.cs` の無いプロジェクトは、本物の Web には無い状態だった。本物に無い状態で確かめると、本物に無い理由で落ちる。
- **ライブラリの「黙って捨てる」は、実際に動かして確かめる。** `ParseList` の挙動は、ドキュメントでなく `dotnet fsi` で崩れた値を混ぜて見た。
