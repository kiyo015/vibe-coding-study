レビュー役の model を実測で決める — 見逃しより怖いのは、もっともらしい誤り

業務ルールを変える手順をスキルにし、レビュー役に業務の観点を足した。誤りを仕込んだ同じ差分を haiku／sonnet／opus に18回レビューさせ、検出・誤り・費用・時間を比べて、レビュー役を opus に決めた。2週目の最終日。

2026-10-06対象: sales-core ／ .claude（エージェント・スキル）段階1 / Day24

エグゼクティブサマリー

  1. レビュー役の model を opus に決めた。11項目の誤りを含む差分で、平均の検出は opus 10.8・sonnet 9.7・haiku 7.0。opus は最も速く（60秒）、誤った記述が0件。費用は sonnet の1.1倍（1回 $0.29）。
  2. haiku の問題は見逃しよりも、存在しない API や合わない計算をもっともらしく書くこと。1回は、仕込んだ税の誤りを「良い点」として褒めた。
  3. 1回目の9回は、すべての model がファイルを読めていなかった。Windows の短縮パスが原因。差分だけのレビュー（Day29 の CI と同じ条件）として使い、読める条件で回し直した。
  4. レビュー役が sales-core に無かったので新しく作った。ルール変更の手順は domain-rule-change スキルにまとめ、新しいセッションで呼ばれることを確かめた。

05今日学んだこと

レビュー役に求めるのは「見つける」ことと「誤ったことを言わない」ことの両方。

  • 安いモデルの問題は、もっともらしい誤り。存在しない API や合わない計算を自信のある書き方で出す。そのまま修正に使えば、新しい誤りが入る。件数の比較だけでは見えなかった
  • 結果を読む前に、道具が想定どおり動いたかを確かめる。ヘッドレス実行では permission_denials を最初に見る。Day23 の「黙って無効なアナライザ」と同じ教訓
  • 観点の一覧に無い誤りを混ぜて測る。一覧に書いたものだけでは「一覧を読めるか」しか測れない。差が開いたのは一覧に無い3種だった
  • 作る側は業務ルールを見落とす。常に読み込んでいても、差分を作った Claude が Day20 の決定に反した。レビュー役が別に読む意味がある
  • Windows の短縮パスは、権限の判定を変える。ヘッドレスで作業ディレクトリを渡すときは長いパスにする

つまずき

  • 9回をまとめて回すと、ツールの時間制限（10分）を超える。途中で止め、子プロセスが残っていないことを確かめてから、独立したプロセスで起動し直した。止めた実行の費用（最大 $0.1 程度）は記録できていない

{
    Require(Status is not SalesOrderStatus.Cancelled, "明細の削除");

// SalesOrderLine.cs — 数量を検査せずに代入（P4・P8）。double（P2）とキャストの切り捨て（P3）。率の範囲を見ない（P10）
internal void ChangeQuantity(decimal quantity) => Quantity = quantity;

{
    var factor = 1 - percent / 100.0;
