# Day24 学習記録（2026-10-06）— ルール変更手順のスキル化とレビュー役の強化

基幹システム開発計画の10日目で、2週目の最終日。業務ルールを変えるときの手順を `domain-rule-change` スキルにまとめ、レビュー役 `team-reviewer` に業務の観点を足した。そのうえで、**誤りを仕込んだ同じ差分を haiku／sonnet／opus に18回レビューさせ**、検出数・誤り・費用・時間を比べて、レビュー役の model を **opus** に決めた。

## 今日行った処理

### 1. レビュー役が sales-core に無かった

sales-core の CLAUDE.md は「マージ前に `team-reviewer` でレビューする」と書いていた。しかし定義は Study 側（`Study/.claude/agents/`）にしか無く、sales-core を開いたセッションからは使えない状態だった。

sales-core に `.claude/agents/team-reviewer.md` を新しく作った。Study の汎用版の観点（要件・境界条件・失敗時・テスト）に、業務の観点を4つ足した。

| 観点 | 主な確認 |
|---|---|
| 金額の型と端数処理 | **型名を書かない double**（`var x = 1.5`、`100.0`）、**キャストによる切り捨て**（`(long)x`）。どちらも Day23 のビルド検査で止まらないので、ここで拾う。消費税は税率ごとに1回、分納・返品は累計差分 |
| 状態遷移 | 新しい操作に状態の検査があるか。出荷後に単価・数量を変えられないか。受注数量を出荷済み数量より小さくできないか |
| 取消と削除 | 受注・売上・請求を物理削除していないか（リストからの `Remove` を含む） |
| 秘密情報 | 接続文字列・パスワードを `appsettings*.json` やコードに書いていないか |

### 2. `domain-rule-change` スキル

`sales-core/.claude/skills/domain-rule-change/SKILL.md`。税率・端数処理・締め日・状態遷移など、業務ルール集の決まりを変えるときの7手順。

| 手順 | 中身 |
|---|---|
| 1. 本人に確かめる | 業務の決まりを決めるのは本人。あいまいなら選択肢を出して決めてもらう |
| 2. 文書を先に直す | 変更日と理由。古い決まりは「いつまでこうだった」を残す |
| 3. テストを先に変える | 古い実装と新しい実装で結果が変わる値を入れ、古い実装のまま狙ったテストが落ちるのを見る |
| 4. 1か所だけ直す | 決まりごとの実装の場所の表（端数処理は `Money.Round` だけ、など） |
| 5. 古い決まりの残りを探す | 古い値や言い回しで検索する |
| 6. 確かめる | 全テスト、対照実験、`team-reviewer` |
| 7. 記録する | コミットメッセージに、変えた決まり・決めた日・確かめたこと |

新しいセッション（haiku）で「標準の消費税率を10%から12%に変えたい」と頼んだところ、`Skill(domain-rule-change)` が呼ばれた。答えも手順どおりで、まず業務ルール集を読み、変更日と軽減税率の扱いを本人に確かめてから「文書 → テスト → コード」の順で進める、という内容だった（$0.05）。

### 3. model 比較の作り方

**差分**: 受注の変更機能（明細の数量変更・明細の削除・受注全体への値引き）と、請求書の請求額。一時的な作業ツリー（`git worktree`）で作り、誤りを10種仕込んだ。

**ビルドはエラー0、テスト109件はすべて成功。** Day23 の申し送りどおり、ビルドで止まる書き方（`Math.Round` や `double` の語）は使っていない。CIでは止まらず、レビューで拾うしかない誤りだけで構成した。

| # | 仕込んだ誤り | 観点の一覧に |
|---|---|---|
| P1 | 請求額に、明細ごとに丸めた税額の合計を使う | 載せた |
| P2 | 値引きの計算が double（`percent / 100.0`） | 載せた |
| P3 | 値引き後の単価を `(long)` キャストで切り捨てる | 載せた |
| P4 | 数量を出荷済み数量より小さくできる | 載せた |
| P5 | 出荷後も単価・数量を変えられ、計上済みの売上と合わなくなる | 載せた |
| P6 | 明細を物理削除する | 載せた |
| P7 | 接続文字列のパスワードを設定ファイルに書く（架空の値） | 載せた |
| P8 | 数量変更で 0・負・小数4桁を検査しない | **載せていない** |
| P9 | 最後の明細を消すと、明細0行の受注になる | **載せていない** |
| P10 | 値引き率の範囲（負・100超）を検査しない | **載せていない** |
| P11 | 伝票全体への値引きは、業務ルールで「扱わない」と決めている | （仕込んだつもりは無かった） |

P8〜P10 を一覧に載せなかったのは、「観点に書いたものは見つかる」以上のことを測るため。

**P11 は最初の試行で haiku が見つけた。** Day20 に本人が決めた「伝票全体への値引きは扱わない」に、仕込んだ差分の値引き機能そのものが違反していた。本物の問題として採点に加えた。

**実行**: `claude -p --agents <定義> --agent team-reviewer --model <m> --setting-sources project --strict-mcp-config`。変えたのは `--model` だけ。`--setting-sources project` で、個人のプラグインや口調を変えるフックを混ぜない。

### 4. 途中で見つけた交絡要因：ファイルを読めていなかった

1回目の9回の出力に、opus が「差分の外のファイルは、Windows の短縮パスが原因で読めませんでした」と書いていた。JSON の `permission_denials` を見ると、**9回すべてで Read・Grep が拒否されていた**（1回あたり1〜8件）。作業ツリーのパスを `%TEMP%`（`C:\Users\SAKAGU~1\…`）から作っていたため、権限の確認で作業ディレクトリの中と認められなかった。

捨てずに2つの条件として使った。

| 条件 | 中身 | 意味 |
|---|---|---|
| A | 短縮パスのまま。ファイルを読めない | 差分だけを見たレビュー。Day29 の CI（差分だけを渡す）と同じ条件 |
| B | 長いパス（`C:\Users\sakaguchi\…`）で回し直し。拒否 0件 | 周りのコードも読めるレビュー。普段の使い方 |

### 5. 結果

18回の出力を、11項目それぞれ「その問題を問題として挙げたか」で採点した。

| | haiku | sonnet | opus |
|---|---|---|---|
| 検出（11項目中、6回の平均） | 7.0 | 9.7 | **10.8** |
| 条件A（差分だけ） | 7.3 | 9.3 | 10.7 |
| 条件B（ファイルも読める） | 6.7 | 10.0 | **11.0**（3回とも満点） |
| 費用（1回） | $0.126 | $0.264 | $0.292 |
| 時間（1回） | 122秒 | 187秒 | **60秒** |
| 誤った記述（1回あたり） | 3.8 | 0.5 | **0** |

項目別に見ると、haiku が苦手だったのは P4（出荷済み数量未満、6回中2回）、P9（明細0行、1回）、P10（値引き率、1回）。sonnet は P6（物理削除を規則違反として挙げる、4回）と P9（2回）。opus が落としたのは P9 の1回だけだった。

**誤った記述**の例:

- haiku: 存在しない `SalesOrderStatus.Accepted`・`Tax.TotalTax`、誤った計算例（「333 × 0.66 → 219円」）、事実と違う説明。単価を `Money.Round` で丸める修正案は、円単位に丸めて銭が消えるので、そのまま入れると新しい誤りになる
- haiku の条件Bの1回は、仕込んだ税の誤り（P1）を「請求額を正しく計算している」と**良い点として褒めた**
- opus は0件。単価の丸めについて「`Money` は円単位しか無いので、単価用の丸めを `Money` に足す」と正しく書き、「1000円×2個を出荷した後に10%引きすると、2個を全部返品しても200円が残る」という具体例も計算が合っていた

### 6. 決めたこと

**レビュー役の model を opus にした**（`team-reviewer.md` に `model: opus`）。

- 検出が最も多く、ファイルを読める条件では3回とも満点。誤った記述が無い
- 最も速い（60秒。sonnet の約3分の1）
- 費用は sonnet の1.1倍、haiku の2.3倍（1回 $0.29）。レビューはマージ前に1回なので、見逃し1件の手戻りより安い

CLAUDE.md の開発の進め方にも、定義の場所と model を選んだ根拠を書いた。

## 今日学んだこと

### 安いモデルの問題は、見逃しよりも「もっともらしい誤り」

haiku は11項目中7項目を見つけた。問題はむしろ、存在しない API を使った修正案や、計算の合わない例を、自信のある書き方で出すこと。読む人がそのまま修正に使えば、新しい誤りが入る。レビュー役に求めるのは「見つける」ことと「誤ったことを言わない」ことの両方で、後者は件数の比較だけでは見えなかった。

### 結果を読む前に、道具が想定どおり動いたかを確かめる

1回目の9回は、すべての model が「ファイルを読めない」状態で動いていた。出力の一文に気付かなければ、「周りのコードを読んだレビュー」として誤って記録していた。Day23 の「最新版のアナライザが黙って無効」と同じで、ヘッドレス実行でも `permission_denials` のような**道具が実際に使えたかの記録**を最初に見る。

### 観点の一覧に無い誤りを混ぜて測る

観点に書いた項目だけを仕込むと、「一覧を読めるか」しか測れない。一覧に無い3種（P8〜P10）で差が開いた（3種 × 6回 ＝ 18点満点で、haiku 6・sonnet 13・opus 17）。

### 仕込んだ差分そのものが、業務ルールに違反していた

「伝票全体への値引きは扱わない」は Day20 に本人が決めたことなのに、差分を作った Claude 自身がそれを忘れて値引き機能を書いた。業務ルール集を常に読み込んでいても、作る側は見落とす。レビュー役が別に読むことに意味がある。

### Windows の短縮パスは、権限の判定を変える

`%TEMP%` は `C:\Users\SAKAGU~1\…` という短縮形で返る。同じ場所でも、Claude Code の権限の確認では作業ディレクトリの中と認められなかった。ヘッドレスで作業ディレクトリを渡すときは、長いパスにする。

**症状** — バックグラウンドで始めた比較が、10分で打ち切られる見込みになった。

### 仕込んだ誤り（差分の抜粋）

```csharp
// SalesOrder.cs — 状態の検査が「取消でない」だけ（P5）。Remove は物理削除（P6）、最後の1行も消せる（P9）
public void RemoveLine(SalesOrderLine line)
{
    Require(Status is not SalesOrderStatus.Cancelled, "明細の削除");
    _lines.Remove(line);
}

// SalesOrderLine.cs — 数量を検査せずに代入（P4・P8）。double（P2）とキャストの切り捨て（P3）。率の範囲を見ない（P10）
internal void ChangeQuantity(decimal quantity) => Quantity = quantity;
internal void ApplyDiscount(int percent)
{
    var factor = 1 - percent / 100.0;
    UnitPrice = (long)(UnitPrice * (decimal)factor * 100) / 100m;
}

// Invoice.cs — 明細ごとに丸めた税額を足して請求額にする（P1）
public Money TotalAmount => Tax.TaxableTotal + LineTaxes.Aggregate(Money.Zero, (total, tax) => total + tax);
```

```
ビルド: エラー 0（double の語もキャスト以外の丸め API も無いので、SALES001・RS0030 に掛からない）
テスト: 109件すべて成功（追加した5件はすべて、割り切れる値・1明細だけの例）
```
