# 経路×ガードの表

設定したガードが**実際の経路で効いているか**の一覧。次月ロードマップのテーマA。

「設定した」と「効いている」は別物。Day7（worktreeの隔離が未追跡ファイルに素通し）、Day11（PowerShellツールにフックが効いていなかった）、Day13（無人実行の`--tools ""`が消えていた）は、どれも設定した時点では気づけなかった。

## 検証状態の区別

- **自動** — `checks/guard-e2e.js`が本物の`claude -p`で対照実験付きで確かめる。ガードを外すと不合格になることも確認済み
- **手動** — 手で1回確かめただけ。その後の変更で壊れても気づけない
- **未検証** — 効くはずだと思っているだけ

## 分かったこと

- **ガードは知らないうちに重なっている。** 対照実験で「フックなしなら実行される」はずが、Claude Code本体の「怪しいパス」検知（`SAKAGU~1`のような8.3形式）に止められた。自分で設定していない層があると、ガードを外しても止まり続け、**自分のガードが効いているのか別の層が効いているのかを区別できない**。対照実験の対象は、他の層に引っかからないもの（作業フォルダ内の存在しない名前）を選ぶ
- 判定では「別の仕組みに止められた」を「ガードで止まった」と分けて扱う。一緒にすると、フックが壊れていても緑になる
- **ガードの効き方には2種類ある。** フックは「試みて止められる」ので差し戻しの文言が残る。`tools`制限は「書く道具がそもそも無い」ので試みることすらなく、文言も残らない（サブエージェントは「持っているのはRead・Grep・Globだけ」と答えた）。後者を副作用（ファイルができたか）だけで判定すると、**サブエージェントが起動せずに終わった場合も合格に見える**。起動・完了の記録（`task_started`／`task_notification`）と、書き込みを試みたのが誰か（`parent_tool_use_id`）も合わせて見る

- **`--tools ""`は「全ツール禁止」ではなかった。** 禁止されるのは組み込みツール（Write・Bashなど）だけで、MCPツールは残る。起動時の記録（`system:init`の`tools`）で数えると、健康診断の無人実行には次のツールが残っていた。
  - `study-progress`（2個・読み取りのみ）
  - claude.aiのコネクタ「Claude Docs」（8個。`create`・`update`・`delete`を含み、**外部サービスへ書き込める**）
  - Canva・Google Driveも接続対象になっていた（認証待ちで使えなかっただけで、認証すれば使える状態）

  `--strict-mcp-config`を足すと0個になった。Day12で「`--tools ""`で全ツールを禁止する」と書いたのは不正確だった。**モデルに「使えるツールを答えて」と聞くより、起動時の記録を見る方が確実**（判定もそちらで行う）

- **「拒否の記録があるか」で判定すると、守れていなくても緑になる。** `permission_denials`は「何かが1回拒否された」としか言っておらず、狙ったファイルを守った証拠ではない。読ませたファイルに目印の文字列を仕込み、**その目印が返ってきていないこと**を主な判定にした上で、拒否の記録は対象ファイルのものだけを数える（2026-09-25 `classifyDeny`）
- **denyルールの対照実験は、ファイル名だけを変えて行う。** 同じリポジトリ・同じツール・同じ頼み方のまま、`.env`（deny対象）と`guard-probe-secret-7f3a.txt`（対象外）を入れ替える。ガードを外すために設定ファイルを差し替えると、他のルールまで一緒に消えて「何が止めたのか」が曖昧になる

- **マーケットプレイスの登録は、マシン全体で名前ごとに1つ。** `Study`は`vibe-study`をローカルフォルダとして、`sales-core`は同じ名前をGitHub（タグ固定）として登録する。起動したプロジェクトが自分の登録で上書きするので、`~/.claude/plugins/known_marketplaces.json`は開くたびに行き来する（2026-09-28 実測）。9/28の時点では、読み込まれる版はどちらも意図どおりだった（Study＝作業中のコード、sales-core＝`cache/vibe-study/dev-guard/1.2.0`）。

**2026-10-21 に、この上書きし合いが安全柵を黙って無効にしていたと分かった。**
- **症状:** sales-coreのセッションで、dev-guardが読み込まれていなかった。DBを壊すコマンドが、PowerShellツールで素通りした（`--dry-run`と存在しないプロジェクト名のおかげで何も消えなかった）。
- **原因:**
  - キャッシュの1.2.0が消えていた。インストールの記録は、Study用の欠けた1.1.0しか残っていなかった。
  - それまで止まっていたのは、Studyの登録（作業中のソース）を読んでいたから。登録がGitHubに切り替わった時点で、読み込みに失敗した。
  - 失敗は`--debug`の記録に`Plugin "dev-guard" not cached`と出るだけで、画面には何も出なかった。
- **対策:**
  - Studyのローカルの目録を別の名前（`plugins/.claude-plugin/marketplace.json`、`vibe-study-local`）にして、上書きし合いを無くした。
  - sales-coreには、GitHubのv1.3.1を`claude plugin install`で入れ直した。
  - 両方のセッションで、読み込み元がそれぞれの目録になったことを確かめた。
- **その他:**
  - `claude -p`のセッションは、バックグラウンドでのマーケットプレイスの取得を終える前に閉じる。取得が終わるまで待つ`claude plugin marketplace add`を使った。
  - `claude plugin marketplace remove`をsales-coreの中で実行すると、プロジェクトの`settings.json`からも登録が消えた（元に戻した）。
  - 新しく参加した人が初日に確かめる手順は、sales-coreの`docs/onboarding.md`にある。

- **対照実験の「安全の根拠」は、環境が変わると崩れる。** Day17・18は「`dotnet-ef`が入っていないので、ガードを外して実行してもエラーで終わる」ことを安全の根拠にしていた。Day19でsales-coreに`dotnet-ef`と`DbContext`を入れた時点で、その対照実験は**本当に開発用DBを消せる**状態になった。ツールを入れる前に、コマンドを`dotnet ef database drop --dry-run --project <存在しない名前>`に変え、環境に頼らず2重に止まる形にした。E2Eの前後で開発用DBのマイグレーションが適用済みのまま残ることも確かめた（2026-09-29）

## Windowsの落とし穴（未確認だった3件の結論、2026-10-20）

- **PowerShell用のdenyルールは`PowerShell(...)`。** 書き方はBashと同じ形で、別名（`Write-Output`のルールは`echo`も止める）と`;`・`|`の複合コマンドも見る（公式ドキュメントどおり）。ただし先頭一致なので、引数の並べ方を変えると抜ける。`Bash(git push -f *)`などと同じ3本をStudyとsales-coreに足した
- **PreToolUseの上の階層の`decision: 'block'`は非推奨だった。** 公式ドキュメントは`hookSpecificOutput.permissionDecision: 'deny'`と`permissionDecisionReason`を使うよう書いている（`block`は`deny`に読み替えられるので、今まで動いていた）。`pre-bash-guard`を移し、BashとPowerShellの両方で止まることを実際のツールで確かめた。PostToolUse（`post-edit-test`）の`decision: 'block'`は今も正式な書き方なので変えない
- **タイムアウトで打ち切っても、孫プロセスは動き続ける。** `execSync`に上限1秒を付けてcmd経由でnodeを起動すると、1.0秒で返るが、孫は4秒後にファイルを書いた。打ち切った後はシェルが消えていて`taskkill /T`も「プロセスが見つからない」で届かない（`evidence/2026-10-20-grandchild.js`）。`post-edit-test`のテストが時間切れになると、`npm test`や`dotnet test`の本体が残る。害が出たら、非同期の`spawn`と自前の時間切れで、シェルが生きているうちに`taskkill /T /F`する
