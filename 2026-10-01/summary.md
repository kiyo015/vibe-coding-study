# Day21 学習記録（2026-10-01）— 消費税

基幹システム開発計画の7日目。消費税の計算を TDD で作り、**税率ごとに1回だけ四捨五入する**（インボイス制度の要件）ことをテストで固定した。誤りの頻度を数えようとして**検証に使っていた乱数の品質の問題**に気付き、昨日（Day20）の報告の数字を訂正した。

## 今日行った処理

### 1. 規則を数字で確かめた

105円（10%）の明細が3行ある請求書の場合:

| 計算の仕方 | 計算 | 税額 |
|---|---|---|
| 明細ごとに丸めて足す（誤り） | 10.5 → 11 を3回 | 33円 |
| 税率ごとに1回（要件） | 315 × 10% ＝ 31.5 → | **32円** |

ありがちな誤りは「明細ごとに税額を出して合計する」こと。明細に税額の欄を持たせると、自然にそう書いてしまう。

### 2. テストを先に書いた（13件）

| テスト | ねらい |
|---|---|
| 対象額×税率を四捨五入 | 基本 |
| **105円×3行で32円** | 丸めの位置で結果が変わる例 |
| 税率混在（10% と 8%） | 税率ごとに集計し、高い税率から並べる |
| ちょうど半円（5円・25円・-25円） | 0 から遠い側へ寄せる。負の対象額も |
| 赤伝と黒伝が同じ請求書 | 対象額も税額も打ち消し合う |
| 税率0% | 対象額だけ集計し、税額は0円 |
| 明細なし | 集計なし、合計0円 |
| 税率の範囲（負・100超・小数3桁）3件 | 作れない |
| **ランダムな請求書1万件** | 税率ごとの対象額・税額・請求額がすべて合う |

**ランダムのテストでは、期待値を製品コードとは別の方法で出した。** 製品コードは `decimal` と `Money` を使う。期待値は `long` の整数計算だけで出す（税率を1万分率で持ち、整数の割り算で四捨五入）。同じ式で期待値を作ると、式が誤っていても両方が同じように誤り、テストが通ってしまう。乱数の種は固定したので、落ちたときに同じ請求書で再現できる。

8% では「ちょうど半円」が起きない（対象額が円の整数である限り、8% を掛けて .5 にならない）ので、半円の境界値は 10% で作った。

### 3. RED → 対照実験 → GREEN

| 段階 | 実装 | 結果 |
|---|---|---|
| RED | 空 | 13件中12件が失敗 |
| 対照 | **明細ごとに丸めて合計**（集計・並べ替え・合計は正しい） | **2件が失敗**: 105円×3行の例と、ランダム1万件 |
| GREEN | 税率ごとに1回丸める | Domain 36件・結合 6件すべて成功 |

対照実験で、**ほかの固定の例は誤った実装でも通る**ことが分かった。税率混在のテスト（1000・500・300・280円）は、明細ごとに丸めても税率ごとに丸めても同じ答えになる。105円×3行のような「丸めの位置で結果が変わる例」を意図して入れていなければ、固定の例だけでは誤りを捕まえられなかった。

```csharp
var taxableAmount = group.Aggregate(Money.Zero, (total, line) => total + line.Amount);
return new TaxSummary(group.Key, taxableAmount, group.Key.TaxOn(taxableAmount));
```

税額の計算（`TaxRate.TaxOn`）は `Money.Round` を呼ぶだけなので、丸めを行う場所は引き続き `Money.cs` の1か所だけ（検索で確認）。

### 4. 誤りの頻度を数えた

「明細ごとに丸める」誤りで、請求書の税額がどのくらいずれるかを数えた（`evidence/2026-10-01-tax-per-line-vs-per-rate.js`。結果は付録）。

| 条件（1請求書 1〜30行） | 税額が食い違う請求書 | 差の最大 |
|---|---|---|
| 1行 -50,000〜500,000円（赤伝を含む） | **53.0%** | 5円 |
| 1行 1〜3,000円（小口の商品） | **53.2%** | 4円 |

**半分以上の請求書で税額が狂う。** 稀な端のケースではなく、日常的に請求額を誤らせる誤り。

### 5. 乱数の品質の問題に気付き、Day20 の数字を訂正した

上の集計の最初の結果に、不自然な点があった。

```
差の分布: ... +3円=157件, +4円=1件, +5円=30件
```

+5円が30件あるのに +4円は1件しかない。金額の性質でこうなるとは考えにくいので、**乱数の作り方を疑った**。使っていたのは線形合同法の剰余で、下位のビットほど周期が短い（最下位ビットは 0 と 1 を交互に繰り返すだけ）。品質の良い乱数（mulberry32）に替えると、滑らかな山形の分布になった。

**昨日（Day20）の分納・返品の検証も、同じ乱数を使っていた。** 測り直すと数字が大きく変わった。

| 方式 | Day20 の報告 | 測り直し（1万件中） |
|---|---|---|
| A: 最後の出荷で差額調整 | 10件 | **1,563件（15.6%）** |
| C: A＋全部返品は残額を戻す | 10件 | **1,171件（11.7%）** |
| B: 累計差分（採用） | 0件 | 0件 |

昨日の乱数では「出荷か返品か」の選択が交互に決まってしまい、ずれが起きる並びがほとんど作られていなかった。

**結論（方式Bを採用）は変わらない。** 方式Bが0件になるのは式の形から決まり、乱数に左右されない。誤っていたのは、採らなかった方式がどのくらいずれるかの数字で、大幅な過小評価だった。

訂正した場所は4つ: 業務ルール集（公開リポジトリ）、計画シート、Day20 の記録の md と html。どれも数字を直したうえで「初版では10件と書いていた」という経緯を残した。メールで送った Day20 の報告については、訂正版の HTML を本人に渡した。C# のランダムテストは .NET の `System.Random` を使っているので、この問題は無い。

### 6. 文書を更新した

- **業務ルール集**: 消費税の節に、計算の規則（税率ごとに1回、0% の扱い、赤伝の扱い）、105円×3行の例、53% の実測値、返品が翌月になる場合の税額の注意を書いた
- **CLAUDE.md**: 禁止事項の表に「消費税を明細ごとに丸めて合計する ／ 強制（テスト）」を足した。計画の「お願いから強制へ」で Day21 に予定していた項目

## 今日学んだこと

### 検証の道具も疑う

昨日は「1万件で検証した」ことで安心していた。数が多くても、乱数が偏っていれば同じような場面ばかりを試していることになる。今日気付けたのは、合計の件数だけでなく**差の分布**を出力していたから。結果を1つの数字にまとめすぎると、道具の異常が見えなくなる。

### 結論が道具に依存するかを切り分ける

方式Bの0件は式の形から決まる。方式Aの件数は乱数に左右される。前者を根拠に決めていたので、結論は崩れなかった。数えた結果を根拠にするときは、「なぜそうなるか」を式でも説明できるかを確かめる。

### 誤りを見つけたら、経緯ごと残す

公開している文書とメールで送った報告の数字が誤っていた。数字だけを直すと、前の版を読んだ人には何が変わったか分からない。訂正の告知を冒頭に置き、初版の数字と原因を書いた。

### 固定の例は「誤りで結果が変わる値」を意図して選ぶ

Day20 の「1.5 では銀行丸めを捕まえられない」と同じ教訓が、消費税でも出た。もっともらしい例を並べるだけでは、誤った実装が素通りする。

### 明細ごとの丸めと、税率ごとの丸めの食い違い

```js
// 明細ごと(誤り): 1行ずつ税額を丸めて足す

// 税率ごと(正): 税率ごとの対象額の合計に、1回だけ税率を掛けて丸める
perRate = Σ roundHalfAway(taxableByRate[bp] * bp, 10000);
```
