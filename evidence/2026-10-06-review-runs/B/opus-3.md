### 指摘

#### Critical(必須修正)

**1. `src/SalesCore.Api/appsettings.Development.json:8-9` — DBのパスワードをリポジトリに書いている**
- 何が問題か：`ConnectionStrings:SalesCore` に、パスワードを含む接続文字列がそのまま入っています。
- なぜ問題か：`CLAUDE.md` の「DBの準備」と禁止事項の表で、接続文字列は user-secrets に入れ、リポジトリには書かないと決めています。コミットすれば履歴に残り、ファイルを消しても取り消せません。
- 直し方：
  - この追加を差分から外し、`dotnet user-secrets set ConnectionStrings:SalesCore "<値>" --project src/SalesCore.Api` で設定してください。
  - すでにコミットやプッシュをしていたら、`salescore_dev` のパスワードを変えてください(`\password salescore_dev`)。パスワードの変更は本人が行ってください。

**2. `src/SalesCore.Domain/Invoice.cs:21-25` — 消費税を明細ごとに丸めて合計している**
- 何が問題か：`LineTaxes` は明細ごとに `TaxOn` で丸めています。`TotalAmount` はそれを合計して請求額にしています。
- なぜ問題か：`business-rules.md` §1・§2 で「消費税は税率ごとに1回だけ」と決めています。これはインボイス制度の要件です。
  - 105円(10%)の明細3行の例で計算すると、`TotalAmount` は 315 + 33 = 348円です。正しくは `Tax.TotalWithTax` の 347円です。
  - 同じ請求書の中で、請求額と税率ごとの内訳(`Tax`)の合計が食い違います。これは請求額の誤りです。
  - コメントには「明細欄の税額と合うように」とありますが、明細ごとの税額を請求書に出すこと自体が、インボイスの税額の決め方と合いません。
- 直し方：
  - `LineTaxes` を削除してください。
  - 請求額が要るなら、`TotalAmount => Tax.TotalWithTax` にしてください。

**3. `src/SalesCore.Domain/SalesOrderLine.cs:57-58` — 値引きの計算に double を使い、キャストで切り捨てている**
- 何が問題か：
  - `percent / 100.0` は、型名を書いていない double です。語として `double` が無いので、SALES001 では止まりません。
  - `(long)(...)` は切り捨てです。四捨五入(`Money.Round`)になっていません。
  - 例：単価 33.33円を10%引きにすると 29.997 になり、`(long)2999.7` で 29.99円になります。四捨五入なら 30.00円です。
- なぜ問題か：金額に double を使うこと、`Money` 以外で端数を処理することは、どちらも `business-rules.md` §1 で禁止しています。ビルドの検査をすり抜ける書き方そのものです。
- 直し方：この操作は指摘4のとおり、まず要否を決め直す必要があります。仮に残す場合は、`decimal` だけで計算し、端数処理は `Money` の中に置いてください(単価を2桁に丸める関数を `Money` に足す)。

**4. `src/SalesCore.Domain/SalesOrder.cs:80-88` — 伝票全体への値引きは、業務ルールで「扱わない」と決まっている**
- 何が問題か：`ApplyDiscount` は受注全体に%の値引きをかけます。
- なぜ問題か：
  - `business-rules.md` §8 に「伝票全体への値引きは扱わない(2026-09-30 決定)。値引きは明細単位で行う」とあります。
  - 業務ルールを変える変更なのに、`business-rules.md` が直っていません。
- 直し方：
  - 要件として本当に要るなら、先に `domain-rule-change` の手順で業務ルールを変えてください(決定と文書の更新)。
  - 要らないなら、この操作を差分から外してください。

**5. `src/SalesCore.Domain/SalesOrder.cs:83` / `SalesOrderLine.cs:58` — 一部出荷・出荷済の受注でも単価を変えられ、計上済みの売上と合わなくなる**
- 何が問題か：検査は「取消ではない」ことだけです。一部出荷や出荷済の受注でも `UnitPrice` を書き換えられます。
- なぜ問題か：
  - `SalesAmount` は現在の単価で計算し直されます。次の `Ship`/`Return` の累計差分(`before = SalesAmount`)は、新しい単価を基準に計算されます。
  - そのため、すでに計上した売上の合計が「手元の数量 × 単価」と一致しなくなります。これは §1 が保証していることです。
  - 例：1000円で2個出荷して 2000円を計上した後、10%引きにしてから1個返品すると、返品は -900円になります。売上の合計は 1100円ですが、手元の1個 × 900円 = 900円と合いません。
  - 確定した売上の金額を、後から実質的に変えることにもなります。
- 直し方：残す場合は、受付・承認済のときだけ許してください。

**6. `src/SalesCore.Domain/SalesOrder.cs:63-71` / `SalesOrderLine.cs:53` — 数量変更に検査が無い**
- 何が問題か：
  - 出荷済み数量より小さくできます。`RemainingQuantity` が負になり、受注数量より多く出荷した状態が残ります。
  - 0・負の値・小数4桁以上を受け付けます。`EnsureQuantity` を呼んでいません。
  - 一部出荷・出荷済でも変えられます。出荷済の受注で数量を増やすと、残りが出ても出荷できないまま「出荷済」に残ります。一部出荷で全部の残りを0にしても、状態は「出荷済」に進みません。
  - `Amount`(明細金額)は計上済みの売上と食い違います。
- なぜ問題か：§3 の「受注数量を超える出荷はできない」に反します。状態と出荷済み数量の整合も崩れます。
- 直し方：
  - 受付・承認済のときだけ許してください。
  - `EnsureQuantity(quantity, ...)` を呼んでください。
  - 一部出荷でも許すと業務で決めたなら、`quantity >= ShippedQuantity` を検査し、状態をもう一度判定してください。

**7. `src/SalesCore.Domain/SalesOrder.cs:73-78` — 受注明細を物理削除している**
- 何が問題か：`_lines.Remove(line)` でリストから取り除いています。
- なぜ問題か：
  - §3・§7 の「物理削除しない。取消は状態で表す」に反します。
  - 一部出荷や出荷済の受注でも消せるので、売上を計上した明細が受注から消えます。その明細は返品もできなくなります(`Validate` で「この受注の明細ではない」になる)。
  - 状態の判定(`All(RemainingQuantity == 0)`)も、消えた明細を数えなくなります。
  - 最後の1行も消せるので、コンストラクタが禁じている「明細0行の受注」ができてしまいます。
  - 受注の明細でない行を渡されても、`Remove` が false を返すだけで何も起きません(失敗を握りつぶしています)。
- 直し方：
  - 明細に取消の状態(例：`IsCancelled`)を持たせてください。
  - 未出荷(受付・承認済)のときだけ許してください。
  - 金額・出荷の判定では、取り消した明細を除外してください。
  - 「明細の取消」を状態ごとの操作の表に足すかどうかは、業務ルールとして決めてください。
