02DbContext の寿命

直す前は、別の人が取り消した受注に、同じ画面から出荷を指示できた。例外にならず黙って通る。

承認するDbContext に「承認済」が残る
別の人が取り消す別の回線
出荷を指示する直す前は通った

CircuitLifetimeTests: 1つのユースケースのインスタンスで操作を続け、画面の回線を再現する。

  • AddDbContextFactory(..., ServiceLifetime.Scoped) にした。工場を scoped にするのは、監査に残す利用者を接続ごとに分けるため。
  • ユースケースの public の操作は、最初に DbContext を作り、終わったら捨てる。
  • 変更の後の読み直しは、参照の検査の無い private の読み込みに分けた（Day38 の持ち越し）。
  • 二重に押した時は、後の方の保存が版数で止まる（409）。
  • AddDbContextFactory は DbContext そのものも登録する。直接受け取る形に戻してもビルドも DI も通るので、UseCaseDbContextTests で止める（AI レビュー2回目で足した）。

03共通部品とマスタ

誤りを状態コードと理由に直す部品を API と画面で共通にした。マスタの画面はその上に乗る。

部品役割
OperationError例外を 401・403・404・400・409 と理由に直す。一意インデックス（11本）の違反は制約ごとの理由で 409。業務の誤りでなければ null（API は 500）
OperationPage画面の基底。操作を包んで誤りを持つ。業務の誤りでない例外は中身を見せずに記録する
ErrorMessage.razor状態ごとの見出しと理由。data-status に状態コード
NavMenu.razor役割に応じたメニュー。入口の検査と同じ表（Permissions.Allows）で決める

マスタの入力の決まり（Domain。誤りは 400）

  • 空にできない。長さはコード20・名前100・単位10で、文字数で数える（「𠮷」も1文字）。
  • コードの前後に空白は入れられない。
  • 標準単価は0以上・小数2桁まで・整数部13桁まで（DB の列は numeric(15,2)）。
  • 請求先は1段まで。画面の選択肢にも、請求先を持たない得意先だけを出す。
  • コードの重複は 409。無効にしたもののコードも使えない。同時に登録された時も、一意インデックスから同じ形の理由になる。

画面のテスト（MasterPageTests・bUnit）

  • 管理者が登録すると一覧に出る。重複は 409、コードが空なら 400 で、どちらも理由が出る。
  • 営業・経理には登録の欄が出ず、一覧は見える。役割の無い利用者には 403 の理由が出る。
  • 標準単価が数でなければ、ユースケースを呼ばずに入力欄で止める。

06学んだこと

長く生きる画面では、DB の接続の寿命がそのまま業務の誤りになる。しかも黙って通る。

  • API では起きなかった問題が、画面で起きる。API はリクエストごとに DbContext ができる。画面は回線の間ずっと同じものが生きる。
  • 便利な登録は、禁止したい形まで通す。AddDbContextFactory は DbContext そのものも登録するので、古い形に戻しても気付けない。決めた形はアーキテクチャテストで守る。
  • 画面のテストの不安定さは、待つ対象で直す。時間を延ばしても直らず、入れた値が画面に入るのを待って直った。
  • 対照実験が0件なら、まず確かめるテストが無いことを疑う。工場の singleton は、テストを足して初めて検出した。

つまずき

  • 編集用の Python をヒアドキュメントで渡すと切れた → ファイルに書いてから実行した。
  • decimal.Round が禁止の API でビルドエラー → * 100m % 1m で端数を確かめた。
  • bUnit で UnknownEventHandlerIdException → 描き直しの後は要素を探し直す。
  • デバッグの markup-debug.html をコミットした → 秘密情報が無いことを見てから消した。
  • 一度だけ DB のテストがすべて準備で落ちた → 再現せず原因不明。Day42 で見張る。
