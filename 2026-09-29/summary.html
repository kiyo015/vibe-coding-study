DB接続とテスト用DBの実証 — 積み上がらない理由を、対照実験で示す

EF Core を入れて空のマイグレーションを開発用DBに通し、結合テストがトランザクションのロールバックで独立することを示した。その前に、ツールを入れることで安全の前提が崩れる箇所を見つけ、先に直した。1週目の振り返りもこの日に行った。

2026-09-29対象: sales-core ／ PostgreSQL 18 ／ EF Core 8段階1 / Day19

エグゼクティブサマリー

  1. 結合テストは3回続けて実行しても成功し、状態が積み上がらない。トランザクションを外した版では2回目に Expected: 0 / Actual: 1 で落ちることを先に見たので、積み上がらない理由がロールバックだと言える。
  2. ツールを入れる前に、対照実験の安全の前提が崩れることに気付いて直した。dotnet-ef を入れると、ガードを外した対照実験が本当に開発用DBを消せた。E2Eの前後で開発用DBが無事なことも実測した。
  3. パスワードを一度も見ずに、接続が正しいことを確かめた。ロールとDBの作成、接続文字列の設定は本人が行い、こちらはマイグレーションの適用が通ることで確認した。
  4. 1週目は予定の作業をすべて完了し、持ち越しは無い。ガードのテストは46件から68件、実効性テストは3セルから6セルになった。

03結合テストが開発用DBを触らないようにする

接続先のDB名が _test で終わらなければ、テストは始まる前に止まる。テストを先に書き、落ちることを見てから実装した。

図表6: 安全装置のテスト（RED で拒否の4件が落ち、GREEN で5件すべて成功）
接続先のDB名期待ねらい
salescore_dev拒否開発用DB
salescore拒否接尾辞なし
salescore_test_backup拒否_test を含むが末尾ではない。「含むか」で判定すると通ってしまう
（指定なし）拒否DB名が無い
salescore_test受け入れテスト用DB

読み返して見つけた落とし穴。AddUserSecrets(assembly, optional: true) は、テストのアセンブリに user-secrets の ID が無いと黙って何も読まない。すると「接続文字列が設定されていない」という原因と違うエラーが出る。テストプロジェクトに API と同じ ID を付け、属性が実際に生成されたことをビルド結果で確かめた。

04ロールバックによる独立を、対照実験で示す

検証用の表をトランザクションの外に作り、「開始時点で0行」を確かめる。2回続けて通ることが、状態が積み上がらないことの証拠になる。

各テストは開始時にトランザクションを始め、終わったらコミットせずに捨てる。表をトランザクションの中で作ると、ロールバックで表ごと消えて、戻し損ねても何も検出できない。外に作っておけば、戻し損ねた行が残り、次の実行で失敗する。
