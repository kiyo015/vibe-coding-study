### 2. 端から端までのテスト（`tests/SalesCore.E2E.Tests`）

| 段階 | 操作 |
|---|---|
| 営業 | ログイン → 受注（支店、ボルト3箱・お茶3本、10/01）→ 承認 → 分納で3回出荷（10/05・10/12・10/19）→ 出荷済 |
| 経理 | ログイン → 本社を 10/31 で締める → 10%: 315円・税32円、8%: 100円・税8円、**計455円** |

- 請求額は、段階1の API だけで通したテスト（`InvoiceApiTests` の最初のテスト）と同じ。営業と経理は、別のブラウザのコンテキストで操作する。
- **画面の起動:** ビルド済みの画面を発行し、環境 `E2E` で別のプロセスとして起動する。
  - Development ではないので、各自の user-secrets（接続文字列・初期の利用者）を読まない。Development で起動すると、本人の利用者とパスワードが端から端まで用の DB に入りうる。
  - テストのプロジェクトは、画面を「先にビルドするだけ」の参照で持つ。無いと、画面だけを直してこのテストを流した時に、古い画面で試してしまう（対照実験の準備中に気付いた）。
- **データ:** マスタと利用者はテストが作る（Domain と `AccountUseCases`）。コードと利用者名は実行ごとに変えるので、前の実行のデータと混ざらず、消さなくてよい（業務のデータは物理削除しない）。パスワードは実行ごとの乱数で、どこにも書き出さない。
- **CI:** 同じ PostgreSQL のコンテナに `salescore_e2e_test` を作り、Chromium を OS の依存ごと入れる（`prepare (e2e)`）。PR を下書きで出して、AI レビューをまわさずに CI だけで先に確かめた。

### 3. 端から端までのテストが見つけた誤り: プリレンダーで入力が消える

| 項目 | 内容 |
|---|---|
| 症状 | 「明細を足す」を押しても2行目が出ず、30秒で時間切れ。スクリーンショットでは、入れた得意先・受注日（10/01 → 今日に戻る）・商品・数量がすべて元に戻っていた |
| 原因 | 画面は先に静的に描かれ（プリレンダー）、少し遅れて接続が繋がり、描き直される。その間に入れた値と押したボタンは失われる。回線が遅い時の利用者にも起きる |
| 対策 | ユースケースを呼ぶ10画面は `@rendermode PageRenderMode.Interactive`（`prerender: false`）で描き、接続が繋がってから中身を出す。描画方式のテスト（`RenderModeTests`）で止める（RED: 10画面すべてがプリレンダーしていた） |
| ついで | 読み込み（ユースケースの呼び出し）が、プリレンダーと接続の後の2回走っていたのも無くなる。ログインしていない時にログインの画面へ回すこと（302）は変わらない |

### 4. Day44 からの持ち越し

- **締めの画面のテストの時計を、日本時間 2030-10-31 01:00 にした。**
  - Day44 は、実行した日（11/05）と同じ日にしていた。
  - 直す時に気付いた。**月末締めの「最近の締め日」は月の中のどの日でも同じなので、実行日とずらすだけでは誤りを見分けられない。**
  - 見分けたい誤りごとに、結果が違う日付になる日を選んだ。サーバーの時計で今日を決めると 2026 年の日付、UTC で決めると 2030-09-30 になる。
- **締め日を空にして送ると、0001-01-01 で送っていた → 画面で止める**（RED を見た）。
  - 請求先の空も画面で止め、両方の理由を出す。
  - ユースケースの「請求先を選ぶ。」は画面から届かなくなるので、API のテストで守る。
- 売上の請求先を読み込まずに締めると止まることのテストを足した。実装は既に止めていたので、最初から通った。対照実験で確かめた。
- 得意先の登録で請求先の読み込みを忘れた時を 500 のままにする理由（プログラムの誤りだから）をコメントに書いた。請求書の一覧の字下げも直した。

### 5. テストと対照実験

| 対照実験（入れた誤り） | 結合 | 端から端まで |
|---|---|---|
| 先に静的に描く（`prerender: true`） | 0 | 1 |
| 静的ファイルを配らない（`UseStaticFiles` を外す） | 0 | 1（確かめを足す前は 0） |
| **ログインの Cookie を読まない（`UseAuthentication` を外す）** | **0** | **0** |
| 締め日の初期値をサーバーの時計で決める | 5 | 0 |
| 締め日の初期値を UTC で決める | 3 | 0 |
| 締め日の空を止めない | 2 | 0 |
| 請求先の空を止めない | 1 | 0 |
| 売上の請求先の読み込みを確かめない | 1 | 0 |

8通りのうち7通りを検出した。数字は落ちたテストの件数（Domain はどれも 0）。

- **`UseStaticFiles` を外しても、最初は端から端までのテストが通った。**
  - 「画面の部品のスクリプト（`blazor.web.js`）は静的ファイルとして配られるので、発行が要る」と思い込んでいた。
  - 発行した `wwwroot` には `app.css` と `SalesCore.Web.styles.css` しか無く、スクリプトはフレームワークが別に配っていた。外して欠けるのは CSS だけで、操作は通る。
  - 操作の間に、読み込みに失敗した要求（400以上、打ち切り以外の失敗）が無いことを確かめる形を足して、検出した。発行が要る理由も「CSS のため」に直した。
  - 画面の移動で前の読み込みが打ち切られる `ERR_ABORTED` は、ブラウザの普通の動きなので除いた。
- **`UseAuthentication` を外しても通るのは、仕組みの事実。** .NET は、認証のサービスの登録を見て、この処理を自動で入れる（Day39 と同じ）。
- 実験の台本で、改行の書き方を誤って1回目が構文の誤りで流れなかった。作業ツリーは変わっていなかった。

### 6. 手元で DB への接続が時間切れになった件

| 項目 | 内容 |
|---|---|
| 症状 | 続けて流すと、3回目と、続く2回がテストの準備で落ちた（`Timeout during reading attempt`。接続を開く途中）。うち1回は5分の上限で打ち切った |
| 調べたこと | 前の実行の画面・テストのホスト・ブラウザのプロセスは0件。PostgreSQL のプロセスは11本（普段どおり）。その時間帯は、プロセスの一覧を取るのに2分以上、`pg_isready` に 1.7〜3.2 秒かかった。結合テスト（`salescore_test`）は普段どおり繋がった |
| 見立て | PC が重い時に、接続が上限（15秒）を超えた。落ち着いてからは通った（15〜21秒） |
| 残すこと | 以前の「DB のテストがすべて準備の段階で落ちた件（原因不明）」も、同じ原因の可能性がある |

## 今日学んだこと

- **本物のブラウザでしか見えない誤りがある。**
  - プリレンダーで入力が消えることは、bUnit（描画方式を見ない）でも、手での確認（人はゆっくり操作する）でも見えなかった。機械が速く操作して、初めて出た。
- **対照実験は、自分の思い込みも試す。**
  - 「スクリプトは静的ファイル」と思い込んでいて、それを理由に画面を発行していた。外す実験で前提が外れていることと、テストが CSS の欠けを見ていないことが、同時に分かった。
- **時計の固定は「実行日とずらす」だけでは足りない。** 見分けたい誤りを書き出し、その誤りごとに結果が違う日付になる日を選ぶ。
- **秘密情報は増やさずに済む形を先に考える。** 新しい接続文字列を置いてもらう前に、既にあるものの DB 名だけを替えれば足りた。本人がパスワードを探す手間も無くなった。
