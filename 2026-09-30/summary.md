# Day20 学習記録（2026-09-30）— 金額型と端数処理

基幹システム開発計画の6日目で、2週目（業務ルールの中核）の初日。`Money` 型を TDD で作り、**テストが「ありがちな誤った丸め」を本当に捕まえるか**を2種類の誤った実装で確かめた。途中で Windows の Smart App Control がビルドした DLL を止める問題に当たり、原因を1つずつ切り分けて確定させた。後半は按分と返品の端数について業務の決めごとを追加し、返品を含めた金額の決め方を1万件の検証で選び直した。

## 今日行った処理

### 1. 落とし穴を先に押さえた：.NET の既定は四捨五入ではない

業務ルール集では、明細金額（単価×数量）も消費税も**四捨五入**。ところが .NET の `Math.Round`・`decimal.Round` は、丸め方を指定しないと**銀行丸め**（ちょうど 0.5 のとき偶数の側に寄せる）になる。

| 値 | 銀行丸め（.NET の既定） | 四捨五入（業務ルール） |
|---|---|---|
| 0.5 | 0 | 1 |
| 1.5 | 2 | 2 |
| 2.5 | **2** | **3** |

負の数（赤伝）も決めた。赤伝は元の伝票の符号を反転したものなので、**丸めが正負で対称（`Round(-x) == -Round(x)`）でなければ、赤伝と黒伝が打ち消し合わず1円残る**。そこで「0.5 は 0 から遠い側へ寄せる」（2.5 → 3、-2.5 → -3。.NET の `MidpointRounding.AwayFromZero`）にした。

### 2. テストを先に書いた（23件）

| まとまり | 件数 | 主な値 |
|---|---|---|
| 円未満は四捨五入する | 11 | 0.4・0.49・0.5・0.51・1.5・2.5・100.5・負の数・DB上限（15桁）の手前 |
| 丸めは正負で対称になり、赤伝と黒伝が打ち消し合う | 4 | 0.5・2.5・49.995・1234.4999 |
| 明細金額は単価と数量の積を四捨五入する | 5 | 1.25×2＝2.5 → 3、33.33×1.5＝49.995 → 50 など |
| 円単位の金額（端数があれば作れない、100.00＝100、加減算） | 3 | |

`decimal` の掛け算は小数5桁（単価2桁＋数量3桁）まで誤差なく出るので、丸めは最後の1回だけで済む。`double` だと 49.995 が 49.99499… になり、49 になりうる。

### 3. RED と2つの対照実験

正しい実装に進む前後で、`Money.Round` の中身を入れ替えて同じテストを流した。

| 段階 | `Money.Round` の中身 | 結果 |
|---|---|---|
| RED | 空（常に0） | 23件中12件が失敗（11件はたまたま通った） |
| 対照① | `decimal.Round(amount)`（指定なし＝銀行丸め） | **7件が失敗**。どれも「ちょうど .5」 |
| 対照② | `Math.Floor(amount + 0.5m)`（よくある自作の四捨五入） | **4件が失敗**。負の数と対称性のテスト |
| GREEN | `decimal.Round(amount, 0, MidpointRounding.AwayFromZero)` | **23件すべて成功** |

- **1.5 のテストは銀行丸めでも通る。** 1.5 → 2 は偶数に寄せても四捨五入でも同じ結果になる。境界値に 1.5 だけを入れていたら、銀行丸めを見逃していた。**切り捨てた側が偶数になる .5**（0.5、2.5、100.5）が要る
- **空の実装でも通っていた「対称性」のテストは意味があった。** 銀行丸めは正負で対称なので落ちないが、Floor 版では黒 3円に対して赤が -2円になり、1円残る。2種類の誤りを、それぞれ別のテストが捕まえる

```csharp
public static Money Round(decimal amount)
    => new(decimal.Round(amount, 0, MidpointRounding.AwayFromZero));
```

`Money.Of` は丸めない。端数のある値が来たら例外にする（黙って丸めると、どこかの丸め忘れに気付けない）。src の中で丸めを行っているのは `Money.cs` の1か所だけであることを検索で確かめた。

### 4. Smart App Control が DLL を止めていた

対照②で最初に `decimal.Floor` 版を入れたとき、**Floor 版でも正しいはずのテストまで落ちた**。結果を信じてコードを直しに行かず、失敗の中身を読んだ。

```
System.IO.FileLoadException : Could not load file or assembly '...\SalesCore.Domain.dll'.
アプリケーション制御ポリシーによってこのファイルがブロックされました。 (0x800711C7)
```

テストの結果ではなく、**DLL の読み込みで止められていた**。設定は変えずに、読み取りだけで証拠を集めた。

- Smart App Control の状態：**1（強制）**
- コード整合性のログに、ブロックのイベント（3033・3077）

仮説「DLL の中身（ハッシュ）ごとに判定が決まる」を、1つずつ変えて確かめた。C# は既定で**決定的ビルド**（同じソースからは同じ DLL）になる。

| 試したこと | DLL のハッシュ | 結果 |
|---|---|---|
| Floor 版（`decimal.Floor`） | `b928…` | ブロック |
| 再ビルドせず再実行 ×2 | `b928…` | ブロック |
| 正しい版に戻す | `80a7…` | 通る（最初に通ったものと同じハッシュ） |
| Floor 版にもう一度 | `b928…` | ブロック |
| 同じ意味で書き方だけ変える（`Math.Floor`） | `65a2…` | 通る |

その後、結合テストで `SalesCore.Infrastructure.dll` も止められた。Microsoft の説明では、署名の無いアプリをクラウドで安全と判断できないとブロックし、**個別に除外する方法は無い**。セキュリティ設定なので選択肢を示し、本人が**オフ**にした。

**止められていた同じ DLL（`0544…`、再ビルドなし）で再実行 → 結合 6件・Domain 23件すべて成功。** 変えたのは設定だけなので、原因は Smart App Control と確定した。CLAUDE.md に、このエラーが出たらテストの成否を判断に使わないことと、対処を書いた。

### 5. 按分の決めごと

本人から「按分に対応できているか」と質問があった。**対応できていなかった**（`Money` に按分の機能は無く、業務ルール集にも決めごとが無い）。

按分では、割り振った金額の合計が元の金額と1円もずれずに一致する必要がある。1,000円を3等分してそれぞれ四捨五入すると 333×3＝999円になる。端数の寄せ方は業務の決めごとなので、選択肢を示して決めてもらった。

| 決めたこと | 内容 |
|---|---|
| 按分の端数 | 比率で割って四捨五入し、**合計との差は金額が最大のもの（同額なら先頭）に寄せる**。1,000円を3等分なら 334・333・333円 |
| 伝票全体への値引き | **扱わない**。値引きは明細単位（単価を下げるか、税率を指定した値引きの明細行）なので、税率ごとの按分は要らない |

比例按分（`Money.Allocate`）は、伝票値引きを扱わないと決めたので当面使う場面が無い。最初に要るのは段階5の会計仕訳なので、その日に作る。

### 6. 返品を含めた金額の決め方を、検証で選び直した

最初は分納について「途中の出荷は単価×数量を四捨五入、最後の出荷で差額調整」（方式A）と決めた。続けて「返品で金額が減った場合も正しいか」と質問があり、**推測で答えずに計算した**。

単価 33.33円・受注3個で、出荷と返品の並びを変えて計算し、さらにランダムな並びを1万件作って「売上の合計が、手元の数量×単価の四捨五入と一致するか」を数えた（`2026-09-30/return-allocation.js`）。

| 方式 | 決め方 | 1万件中の不一致 |
|---|---|---|
| A | 最後の出荷だけ差額調整、返品は単価×数量を四捨五入 | **10件**（1個ずつ全部返品しても1円残る） |
| C | Aに「全部戻す返品は残りの全額」を足す | **10件**（一部を返品した状態でずれる） |
| **B（累計差分）** | 動いた後の累計数量×単価の四捨五入 − 動く前の累計数量×単価の四捨五入 | **0件** |

方式Bは、すべてを足すと途中の項が打ち消し合うので、**合計はどの時点でも必ず「手元の数量×単価」の四捨五入になる**。実験で一致したのは偶然ではなく、式の形から必ずそうなる。弱点は、1回分が単価×数量と1円違うことがあること（1個の返品が34円など）。本人が方式Bを選び、業務ルール集を書き直した。分割入荷と仕入の返品も同じ規則。実装は受注明細と出荷の型を作る Day22 で行う。

## 今日学んだこと

### 境界値は「誤りが結果を変える値」を選ぶ

1.5 は境界値に見えるが、銀行丸めでも四捨五入でも結果が同じなので、この誤りを検出できない。境界値を選ぶときは「**どの誤った実装なら、この値で結果が変わるか**」から考える。

### テストの価値は、誤った実装を入れて確かめる

空の実装で通ったテストは、それだけでは役に立つか分からない。ありがちな誤りを2種類入れてみて、各テストの役割（銀行丸めを捕まえるテスト、Floor 版を捕まえるテスト）が初めて分かった。ガードの E2E で身につけた対照実験の考え方が、単体テストにもそのまま使えた。

### 失敗したら、まず失敗の中身を読む

Floor 版の予想外の失敗を、そのまま「Floor 版の結果」として受け取っていたら、テストかコードの問題だと誤解していた。落ちたのはテストではなく DLL の読み込みだった。原因は1つずつ変えて確かめ、最後は設定だけを変えて同じ DLL で再実行し、言い切れる形にした。

### 一部を特別扱いしても、端数の穴は塞ぎきれない

方式Aに「全部返品のときだけ特別扱い」を足した方式Cでも、ずれは直らなかった。端数の問題は、**合計が必ず一致する形の式**（累計差分）に変えると根本から消える。特別な場合を足していく直し方は、見落とした場合で必ず漏れる。

### 質問には計算で答える

「返品でも正しいか」に対して、推測で「大丈夫」と答えていたら方式Aのまま実装していた。1万件の検証で、1万件に10件という、手で数例を試しただけでは見つからない頻度のずれが見えた。

## 付録：分納・返品の方式を比べた検証の中身

スクリプト本体（`return-allocation.js`）はメールに添付しない（`.js` は実行できる形式として、メールで危険な添付と扱われる）。比べた式と実行結果をここに載せる。金額は円、単価は銭（1/100円）の整数で持ち、四捨五入は 0 から遠い側へ。

```js
// 方式A: 途中の出荷は単価×数量を四捨五入、残数量がゼロになる出荷は差額。返品は単価×数量を四捨五入
if (q > 0 && net + q === orderQty) amount = orderAmount - sum;       // 最後の出荷
else amount = Math.sign(q) * lineAmount(priceSen, Math.abs(q));

// 方式C: 方式Aに「残数量が0になる返品は、残っている売上の全額を戻す」を足す
else if (q < 0 && net + q === 0) amount = -sum;

// 方式B(累計差分): 動いた後の累計数量の金額 − 動く前の累計数量の金額。出荷も返品も同じ式
amount = lineAmount(priceSen, net + q) - lineAmount(priceSen, net);
```

単価 33.33円・受注3個での実行結果（A と B）:

```

B 1個ずつ出荷                   各回=[33, 34, 33]                 合計=100  正しい金額=100  OK
A 1個ずつ出荷 → 1個ずつ全部返品 各回=[33, 33, 34, -33, -33, -33]  合計=1    正しい金額=0    NG(+1円)
B 1個ずつ出荷 → 1個ずつ全部返品 各回=[33, 34, 33, -33, -34, -33]  合計=0    正しい金額=0    OK
A 一括出荷 → 1個ずつ全部返品   各回=[100, -33, -33, -33]         合計=1    正しい金額=0    NG(+1円)
B 一括出荷 → 1個ずつ全部返品   各回=[100, -33, -34, -33]         合計=0    正しい金額=0    OK
A 一括出荷 → 1個返品 → 再出荷  各回=[100, -33, 33]               合計=100  正しい金額=100  OK

```

ランダムの条件: 単価 0.01〜999.99円、受注数 1〜9個、出荷・返品を1〜8回。乱数の種を固定しているので、何度実行しても同じ結果になる。スクリプトはファイル・ネットワーク・他のプロセスに触れない計算だけのもの。本体は [GitHub（タグ day20）](https://github.com/kiyo015/vibe-coding-study/blob/day20/2026-09-30/return-allocation.js) で読める。現在は `evidence/2026-09-30-return-allocation.js` に移してある（日別フォルダには添付できる md と html だけを置くため）。
