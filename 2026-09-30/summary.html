金額型と端数処理 — テストが誤った丸めを捕まえることを、誤りを入れて確かめる

Money 型を TDD で作り、2種類のありがちな誤った丸めで各テストの役割を確かめた。途中で Smart App Control による DLL のブロックを切り分けた。後半は按分と返品の端数の決めごとを加え、返品を含む金額の決め方を1万件の検証で選び直した。

2026-09-30対象: sales-core ／ SalesCore.Domain段階1 / Day20

エグゼクティブサマリー

  1. 丸めは Money.Round の1か所だけになり、境界値を含む23件のテストが通った。丸め方は四捨五入（0.5は0から遠い側）。.NET の既定の銀行丸めは使わない。
  2. テストは2種類の誤った丸めを捕まえる。銀行丸めは7件、「0.5を足して切り捨て」は4件が失敗した。1.5のテストだけでは銀行丸めを見逃すことも分かった。
  3. 予想外の失敗は Smart App Control による DLL のブロックだった。ハッシュごとに1つずつ切り分け、設定だけを変えて同じ DLL で再実行し、原因を確定した。
  4. 返品を含む金額は「累計差分」で決めた。最後の出荷で差額調整する方式は1万件中1,563件でずれ、累計差分は0件。式の形から必ず一致する。

訂正（2026-10-01）。初版では方式A・Cの不一致を「1万件中10件」と書いていたが、正しくは方式Aが1,563件、方式Cが1,171件。検証に使った乱数（線形合同法の剰余）の品質が低く、出荷と返品の選び方が偏っていたための過小評価だった。Day21 に乱数を替えて測り直した。結論（累計差分を採用）は変わらない。累計差分が0件であることは式の形から決まり、乱数に左右されない。本文の数字は訂正後のもの。

01落とし穴：.NET の既定は四捨五入ではない

Math.Round と decimal.Round は、丸め方を指定しないと銀行丸めになる。業務ルールの四捨五入とは、ちょうど .5 のときに結果が変わる。

図表1: 銀行丸めと四捨五入
値銀行丸め（.NETの既定）四捨五入（業務ルール）備考
0.501結果が違う
1.522同じ結果。このテストだけでは誤りを見逃す
2.523結果が違う
-2.5-2-30から遠い側に寄せると正負で対称

赤伝は元の伝票の符号を反転したもの。丸めが正負で対称（Round(-x) == -Round(x)）でなければ、赤伝と黒伝が打ち消し合わず1円残る。そこで MidpointRounding.AwayFromZero を明示した。

04按分と返品の決めごと

割り振った金額の合計は、元の金額と1円もずれずに一致させる。返品を含めると、最後の出荷だけ差額調整する方式では足りなかった。

決めたこと（2026-09-30）
按分の端数
比率で割って四捨五入し、合計との差は金額が最大のもの（同額なら先頭）に寄せる。1,000円の3等分は 334・333・333円
伝票全体への値引き
扱わない。値引きは明細単位なので、税率ごとの按分は要らない
分納・返品の金額
累計差分：動いた後の累計数量×単価の四捨五入 − 動く前の累計数量×単価の四捨五入。分割入荷と仕入の返品も同じ
図表6: 累計差分の例（単価 33.33円 × 受注3個）
動き動いた後の累計計算金額
1個出荷1個33 − 033円
1個出荷2個67 − 3334円
1個出荷3個100 − 6733円
1個返品2個67 − 100-33円
1個返品1個33 − 67-34円
1個返品0個0 − 33-33円
全部出荷すると 100円（受注明細の金額）、全部返品すると 0円0円

すべてを足すと途中の項が打ち消し合うので、合計はどの時点でも必ず一致する。代わりに1回分が単価×数量と1円違うことがある（34円）。方式Cのように特別な場合を足す直し方では、一部を返品した状態のずれが残った。

05今日学んだこと

境界値もテストも決めごとも、「誤りがあったら結果が変わるか」で確かめる。

  • 境界値は「誤りが結果を変える値」を選ぶ。1.5は境界値に見えるが、銀行丸めを捕まえられない
  • テストの価値は、誤った実装を入れて確かめる。空の実装で通ったテストも、誤りを入れて初めて役割が分かった
  • 失敗したら、まず失敗の中身を読む。落ちたのはテストではなく DLL の読み込みだった
  • 特別な場合を足す直し方は、見落とした場合で漏れる。合計が必ず一致する形の式に変えると、根本から消える
  • 質問には計算で答える。ずれの頻度（方式Aで約16%）は、手で数例試すだけでは分からない

付録分納・返品の方式を比べた検証の中身

図表5の根拠。スクリプト本体は添付せず、比べた式と実行結果をここに載せる。

金額は円、単価は銭（1/100円）の整数で持ち、誤差を出さない。四捨五入は 0 から遠い側へ（Money.Round と同じ）。

// 方式A: 途中の出荷は単価×数量を四捨五入、残数量がゼロになる出荷は差額。返品は単価×数量を四捨五入
if (q > 0 && net + q === orderQty) amount = orderAmount - sum;       // 最後の出荷
else amount = Math.sign(q) * lineAmount(priceSen, Math.abs(q));

// 方式C: 方式Aに「残数量が0になる返品は、残っている売上の全額を戻す」を足す
else if (q < 0 && net + q === 0) amount = -sum;

// 方式B(累計差分): 動いた後の累計数量の金額 − 動く前の累計数量の金額。出荷も返品も同じ式
amount = lineAmount(priceSen, net + q) - lineAmount(priceSen, net);
