01決めたこと（本人の決定）

「Day16 に決定済み」だったのは「100万円以上は管理者が承認する」ことだけ。いつ承認待ちになるかは、作業の前に聞いた。

質問決定
税抜合計100万円以上の受注は、いつ・どうやって「承認待ち」になる？登録の時に自動で承認待ち。未満なら今までどおり受付で始まる

決定に合わせて業務ルール集に書いたこと

項目決まり
境界ちょうど100万円は承認待ち
比べる金額税抜合計。税込で超えても、税抜で未満なら受付
承認できる人承認待ちは管理者だけ（営業は API で 403）
基準額を変えた時登録済みの受注の状態は変えない（判定は登録の時の基準額）
取消・却下承認待ちも営業・管理者が取り消せる。管理者が承認しない時も取消
基準額の設定SalesCore:ApprovalThreshold（円）。無ければ100万円。負・円未満の端数は誤り、0 は全件承認待ち

業務フローの状態の図は「受付 → 承認待ち」と描いてあり、決定と食い違っていた。「登録 → 承認待ち」に直した。

02作り

分かれ目は登録の時に1回だけ決める。承認の入口は状態を見るだけなので、基準額を後で変えても扱いがぶれない。

受注の登録SalesOrder(明細, 基準額)
税抜合計で判定≥ 基準額 → 承認待ち
承認の入口承認待ちなら管理者だけ
出荷承認済からだけ
  • Permissions に ApprovePendingSalesOrder（管理者だけ）を足した。ApproveAsync は、受注が承認待ちならこれも確かめる。
  • ApprovalThreshold が設定を読む。API と画面は起動の直後に1回読み、設定の誤りを最初の受注の登録（500）でなく起動で止める。
  • 状態は文字列で保存しているので、マイグレーションは要らない。承認の記録の表（sales_order_approvals）はまだ作らず、承認した人は更新者と監査ログに残る。

03境界値のテスト

税込で100万円を超える 999,999円でも、税抜で未満なら受付で、営業が承認できる。

税抜合計（税込）登録の時の状態営業が承認管理者が承認
999,999円（1,099,999円）受付できるできる
1,000,000円（1,100,000円）承認待ち拒む（403）できる
1,000,001円（1,100,001円）承認待ち拒む（403）できる
  • 承認待ちのままでは出荷を指示できず、管理者が承認すると指示できる。承認待ちは営業も取り消せる。
  • 基準額を後で下げても、受付で登録した受注は営業が承認できる。明細を合わせて届けば承認待ち（合計で比べる）。
  • 状態×操作の表に承認待ちの4通りを足した（全24通り）。PermissionTests の「100万円以上」の行は、承認待ちの受注を毎回作って6通りの利用者で確かめる。
  • API: 設定が無ければ100万円、50万円に設定すればその額で判定する。設定が負なら API は起動しない。
  • 先に RED（Domain 7件・結合 3件・起動の確かめ 1件）を見てから実装した。

06学んだこと

「決定済み」と書いてあっても、決まっているのは一部だけのことがある。作る前に文書の食い違いを探す。

  • 「決定済み」を疑う。決まっていたのは「誰が承認するか」だけで、「いつ承認待ちになるか」は空いていた。図はそのまま作ると決定と違う動きになる形だった。
  • 権限の分かれ目を状態で決める。承認の時に金額で判定し直すと、基準額を変えた時に登録済みの受注の扱いが変わる。登録の時に状態を決めれば、入口は状態を見るだけで済む。
  • テストの外側を先に書き出す。思いつきで並べた誤りでは出てこなかった「起動で設定を読まない」経路が見えた。
  • 状態が変わる操作の全組み合わせは、毎回新しい対象で試す。管理者が承認すると承認済になり、同じ受注で次の利用者を試せない。

つまずき

  • PermissionTests の編集が「File has not been read yet」で空振り → 編集の前に読んでいなかった → 読んでから編集し直した。
  • 決定の記録が Study 側にできた → 前日と同じ → 秘密情報が無いことを見てから sales-core へ移した。
