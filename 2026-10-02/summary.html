受注の状態遷移と分納 — 未出荷のまま請求するコードは、書けない

受注 → 出荷 → 売上 → 請求の流れを Domain に作った。請求書は売上からしか作れず、売上は出荷の確定からしか生まれない。分納と返品の金額は累計差分で実装し、ランダムな並び1万件で売上の合計が常に合うことを確かめた。

2026-10-02対象: sales-core ／ SalesCore.Domain段階1 / Day22

エグゼクティブサマリー

  1. 未出荷のまま請求しようとする書き方は、12通り試してすべてコンパイルエラーになった。請求書の入口は売上だけを受け取り、売上は外のコードから作れない。
  2. 状態の飛び越し・逆戻り・受注数量を超える出荷は、テストで止まる。状態 × 操作の全20通りを並べた。誤った実装14種を入れて、すべて検出された。
  3. 分納と返品の金額は累計差分で実装した。出荷 24,688回・返品 26,849回のすべてで、売上の合計が「手元の数量 × 単価の四捨五入」に一致した。うち 15.7% は、動いた分だけを丸める方式ならずれていた。
  4. 実装のときに決めた業務の決まりが4点あり、本人の確認を待っている。返品しても受注の状態は戻さない、など。

01何を型で止め、何をテストで止めるか

型にしたのは「請求書は売上からしか作れない」という境界1つ。受注の状態は、表を網羅するテストで守る。

受注受付 → 承認済
出荷指示数量は動かない
出荷確定ここで売上が生まれる
売上外からは作れない
請求書売上だけを受け取る

図表1: 請求までの流れ。濃い部分が型で守られている境界

図表2: 守りたいことと、止め方
守りたいこと止め方仕組み
未出荷のまま請求しないコンパイル請求書の入口は売上だけを受け取る。売上のコンストラクタは公開していない
状態を飛び越えない・逆戻りしないテスト受注は1つのクラスで、状態は enum。許されない操作は例外になる
受注数量を超えて出荷しないテスト指示のときと確定のときの両方で確かめる

受注の状態ごとに別のクラスを作れば、状態の飛び越しもコンパイルで止まる。採らなかったのは、Day25 に EF Core で保存するとき、状態が変わるたびにクラスを載せ替える必要が出て重くなるため。

出所: SalesOrderTests の「状態ごとに許される操作だけができる」。できない操作は例外になり、状態が変わらないことまで確かめる

受注を渡す、売上を直接作る、状態を書き換える。どの書き方も、ビルドの時点で止まる。

05分納と返品の金額：累計差分

動いた分だけを丸めると合計がずれる。累計で丸めた金額の差を取れば、どう並べても合う。

図表7: 単価 33.33円 × 3個を1個ずつ出荷し、1個ずつ返品する
動き手元の数量計算金額
1個出荷133.33 → 33 から 0 を引く33円
1個出荷266.66 → 67 から 33 を引く34円
1個出荷399.99 → 100 から 67 を引く33円
1個返品267 から 100 を引く-33円
1個返品133 から 67 を引く-34円
1個返品00 から 33 を引く-33円

期待値は Day21 と同じく、製品コードとは別の方法（単価を銭、数量を 1/1000 の整数で持つ long の計算）で出した。Day21 の教訓から、乱数が偏って確かめたい場面を通らないまま合格していないことを、上の件数に下限を置くアサーションで確かめている。

業務ルール集に無かった4点を、既存の方針に沿って決めた。違っていれば直す。

図表9: Day22 に決めた業務の決まり
#決めたこと理由
1返品しても受注の状態と出荷済み数量は戻さない。返品数量は別に持つ出荷済み数量が増えるだけなら、状態は逆戻りしない

07今日学んだこと

型で止める場所は境界に絞り、内側は表を網羅するテストで守る。

  • 型で止める場所は、境界に絞る。すべての状態を型にすると、保存や画面とのつなぎが重くなる。境界1つを型にするだけで、12通りの書き方が書けなくなった
  • 空の実装で通るテストは、検証が弱い。落ちた件数だけでなく、落ちなかったテストを一覧にして、なぜ通ったかを1件ずつ確かめる
  • 表を網羅するテストは、個別の例が見落とす誤りを捕まえる。「できないこと」は意識して並べる
  • 型による保証は、後から崩れないように固定する。保証の前提（コンストラクタを公開しない）そのものをテストにする

つまずきと未解決の点

  • 対照実験のスクリプトが最初の1件で止まった。Windows PowerShell 5.1 では、Stop の設定のまま標準エラーを結合すると、テストの失敗の出力が例外になる。書き換えたファイルは必ず戻す作りにしていたので、製品コードは元のままだった
  • テストの実行時間の増分が測れていない。Domain のテストが約1秒から7〜8秒になったが、測ったときPCのCPU使用率が94〜100%で、Day21 までの36件だけでも3秒かかった。負荷の無い状態で測り直す
  • 結合テストのビルドで EF Core の版の競合の警告（MSB3277）。今日の変更とは関係が無い。Day25 で揃える

付録検証の中身

図表5・6・8の根拠。スクリプト本体は添付せず、入れた誤りと結果をここに載せる。

対照実験で入れた誤り（抜粋）。「正」が製品コード、「誤」が入れ替えた行。

M01 出荷ごとに丸める
  正: return new SalesRecordLine(quantity, UnitPrice, TaxRate, SalesAmount - before);
  誤: return new SalesRecordLine(quantity, UnitPrice, TaxRate, Money.Round(UnitPrice * quantity));
  → 失敗 2件: 分納の金額は累計数量で丸めた金額の差で決まり… ／ ランダムな出荷と返品の並びでも…

M03 承認していない受注でも出荷できる
  正: Require(Status is Approved or PartiallyShipped, "出荷");
  誤: Require(Status is Received or Approved or PartiallyShipped, "出荷");
  → 失敗 1件: 状態ごとに許される操作だけができる(受付, 出荷指示, 許されない)

M08 返品で出荷済み数量を戻す
  正: ReturnedQuantity += quantity;
  誤: ShippedQuantity -= quantity;
  → 失敗 6件: 返品しても受注の状態と出荷済み数量は戻らない ／ ランダム1万件 ほか

M09 売上のコンストラクタを公開する
  正: internal SalesRecord(DateOnly recordedOn, ...)
  誤: public SalesRecord(DateOnly recordedOn, ...)
  → 失敗 1件: 売上と出荷と請求書は_外から直接は作れない(SalesRecord)

// テスト: 単価は銭、数量は 1/1000 の整数で持つ。decimal も Money も使わない
