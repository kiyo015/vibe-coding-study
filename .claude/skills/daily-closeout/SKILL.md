# その日の作業のクローズ作業

その日の作業と学びを記録に残すための定型作業をまとめて実行する。Day1〜3で毎回手作業で繰り返していた手順をスキル化したもの。

## 対象リポジトリ（Day15以降）

| リポジトリ | 役割 |
|---|---|
| `C:\Users\sakaguchi\Study` | **記録の置き場所**。日別フォルダの成果物と計画シート。GitHub: `kiyo015/vibe-coding-study` |
| `C:\Users\sakaguchi\sales-core` | 基幹システムの製品コード。GitHub: `kiyo015/sales-core`（private） |

**記録は常にStudy側に作る**（製品コードと記録を分ける方針）。その日に`sales-core`を触っていれば、両方のリポジトリをコミットし、**同じタグ`day{N}`を両方に打つ**（成果物リンクをどちらのリポジトリでも固定するため）。Studyしか触っていない日は、Studyだけで完結してよい。

## なぜこの手順か

学習の価値は「その日何をやったか」が後から追える形で残ることにある。手順を省略すると、次回セッション開始時に前回の到達点が分からなくなったり、GitHub上の学習記録が古いままになったりする。特にDay1で復元不能になった過去の失敗（バージョン管理前にファイルを上書きして過去の状態を失った）を繰り返さないよう、**必ずcommitしてから記録を書く**順序を守る。

`Study`全体が単一のgitリポジトリ（`vibe-practice`も配下に含む）。個別に`vibe-practice`だけコミットする必要はなく、下記Step1・Step2の変更を含めてStep3で一括コミットする。

## 手順

### 1. 今日の学習内容をまとめる

`{YYYY-MM-DD}/summary.md` をプロジェクトルート直下に新規作成する（日付はその日の日付）。構成は以下を踏襲する（Day1〜4のsummary.mdを参考にする）:

- タイトル・対象Day
- 今日行った処理（何を作った/直したか、コマンドと**実測値**、動作確認の結果）
- 今日学んだこと（仕組みの理解、実測で分かったこと、思い込みが外れた点）
- つまずき（あれば。症状・原因・対策の形で）
- 気づき・発見（あれば）
- **成果物** — 生成・変更したファイルへのGitHubリンクを列挙する（下記参照）
- 次回予告（計画シートの翌Dayと、持ち越した未完了項目）

会話の中でその日実際に扱った内容を反映すること——テンプレートを機械的に埋めるのではなく、その日固有の学びを書く。

**成果物リンクの書き方** — 触ったリポジトリごとに、そのリポジトリのURLで書く。どちらも**その日のDay番号のタグ**で固定する（タグはStep3でコミット後に打つ）。

| ファイルの場所 | リンクの形 |
|---|---|
| `Study`配下 | `https://github.com/kiyo015/vibe-coding-study/blob/day{N}/<相対パス>` |
| `sales-core`配下 | `https://github.com/kiyo015/sales-core/blob/day{N}/<相対パス>` |

タグにする理由: 以前は`master`参照にしていたが、Day10で2つの問題が判明した。(1) リンク先のファイルが後日更新されると、過去の記録から新しい版が見えてしまう（その日時点の内容を指せていなかった）。(2) リンク先のファイルを移動・削除すると過去の記録のリンクが切れる。コミットハッシュ固定なら両方防げるが、commit前にはハッシュが確定しない。**タグ名はcommit前から決まっているので事前に書け、打った時点に永続的に固定される。**

### 1-2. 同じ内容のHTML版を作る

`summary.md`を書き終えたら、同じフォルダに`{YYYY-MM-DD}/summary.html`を作る。mdが記録の正本、HTMLは人に読ませる配布用という位置づけ。学習記録はメールに添付して送るので、GitHub上でソース表示になるmdだけでは読みにくい。

- **作る前に`html-report-design`スキルを読み込み、そのデザイン規則（CSSをそのまま使う・枠線カードや絵文字なし・各セクションにメッセージ行）に従う**
- 内容はmdと同じ。ただし文章を写すのでなく、比較は表、手順や流れは矢羽根、数値の差はSVGの横棒グラフなど、**図表中心に組み直す**。お手本は`2026-09-11/summary.html`（Day10）
- **1ファイル完結にする。** CSSはインラインで書き、外部のフォントやスクリプト、画像は読み込まない。メール添付で開いてもそのまま見られるようにするため。目安は数十KB以内
- 成果物リンクはmdと同じく`blob/day{N}/...`のタグ固定にする
- 書いたら、レイアウトが崩れていないか実際に描画して確認する。プレビューペインが非表示だと描画されないので、ヘッドレスChromeで画像化して見る（`chrome.exe --headless=new --screenshot=<出力先> --window-size=860,9000 file:///<パス>`）。スクリーンショットはスクラッチパッドに置き、リポジトリに入れない

mdとHTMLをこのStep1で両方作ってからStep3でコミットすることで、`day{N}`タグに2つとも含まれる（Day10ではHTMLをタグの後から追加したため、`day10`にHTMLが入っていない）。

### 2. 計画シートを更新

**現在の計画シートは`study_plan_next_month.md`**（Day15以降）。`study_plan_2weeks.md`はDay1〜14で完了済みなので触らない。

- 該当Dayの節に、実施内容の要約と**実測値**を追記し、見出しに完了の印（✅ 完了）を付ける
- 末尾の「日々の記入欄」の表を埋める（日付・主な内容・完了チェック）
- **未完了の項目があれば、翌Dayの節の先頭に書き写す**（洗い出して終わりにしない）
- 予定と違うことをした場合は、予定を書き換えるのでなく「予定と違う点」として残す

### 3. コミット・タグ・push（触った全リポジトリ）

**製品コード（`sales-core`）を先に、記録（`Study`）を後に**コミットする。記録のリンクが指す先を先に確定させるため。

その日に`sales-core`を触っていれば、そちらで:

```
git -C C:/Users/sakaguchi/sales-core add -A
git -C C:/Users/sakaguchi/sales-core commit -m "<その日の内容が分かる日本語メッセージ>

<その時点でシステムから指示されているCo-Authored-By行>"
git -C C:/Users/sakaguchi/sales-core tag day{N}
git -C C:/Users/sakaguchi/sales-core push
git -C C:/Users/sakaguchi/sales-core push origin day{N}
```

続いて`Study`で同じことをする（`git add -A` → commit → `git tag day{N}` → `git push` → `git push origin day{N}`）。

- **タグ名は両リポジトリで同じ`day{N}`**。Step1で書いたリンクと一致させる。打たないとsummary.mdのリンクが404になる
- その日のうちに`sales-core`側でコミット済みのものがあれば、締めではその後の差分だけをコミットし、タグは最新のコミットに打つ
- `Co-Authored-By`の行は、その時点でシステムから指示されている文言をそのまま使う。モデル名をこのスキルに固定で書かないこと（以前`Claude Sonnet 5`と固定で書いていたが、使用モデルが変わって古くなった）
- push先は既存のリモート（`origin`）にそのまま行う。新しいリポジトリを作ったりリモートを変更したりはしない

### 4. 健康診断で締める

`node checks/health-check.js`（Study側）を実行し、全項目OKを確認する。NGが出たら、その内容も報告に含める。

## 完了後の報告

何をコミットしたか（リポジトリごとのコミットハッシュとタグ）、summary.mdとsummary.htmlのパス（HTMLはファイルサイズも）、健康診断の結果、翌Dayの予定と持ち越しを簡潔に報告する。
