見積（Domain と永続化） — 状態×操作の16マスを固定し、明細の桁を Domain で止めた

見積と見積明細を作った。状態は作成中 → 提出済 → 受注済／失注で、どの状態で何ができるかは作業の前に本人に聞いて決めた。金額と税は受注と同じ計算にした。DB は表2つと有効期限の制約を足した。あわせて、Day42 から持ち越していた明細の桁を Domain で止めた。

04明細の桁を Domain で止めた

DB の列に入らない桁は、Domain で先に止める。DB まで来た桁あふれは利用者の誤りでないので、400 にせず 500 で気付けるようにした。

表4　明細の桁（受注明細と見積明細で共通の SalesOrderLine.EnsureLine）
項目DB の列Domain で止める
数量numeric(15,3)整数部12桁まで
単価numeric(15,2)整数部13桁まで
明細金額—15桁まで
  • 数量の整数部の確かめは、小数の桁の確かめ（×1000）より前に置く。decimal の最大値を入れると、×1000 で計算があふれて別の例外になるため。
  • DB の桁あふれ（22003）は、OperationError の 400 から外した。受注の API の桁のテストは、Domain が止める形で 400 のまま通る。

PR #24 の Minor の片付け

  • 単価の初日に 0001-01-01 を入れると 500 になった。前日は、閉じる単価がある時だけ計算する。
  • 2人が同じ無期限の単価を同時に改定するテストを足した（後の方は 409）。
  • 単価の画面の「閉じた・続けた単価」の知らせを、一覧の前後の差でなく、ユースケースの登録の結果（CustomerPriceRegistration）から作る。ほかの管理者の登録を拾わない。

07今日学んだこと

集約の中の更新は、子を変えたら親の版数も上げる約束にしないと、楽観ロックがすり抜ける。

  • 「親の版数」は、子の行だけを更新すると上がらない。受注で作ってあった仕組みを、見積を足した時に広げ忘れていた。
  • DB の制約は、Domain の検査を外しても残る第2の柵になる。逆に、その柵があるとテストは別の検査を確かめたことにならない。
  • 桁の検査は、順番も決まりのうち。1回目は 1025 で確かめていて、×1000 してもあふれず、順番の誤りを検出できなかった。
  • 「入力の誤り」と「システムの誤り」を混ぜない。DB の桁あふれを一律 400 にすると、集計のあふれまで利用者のせいになる。
